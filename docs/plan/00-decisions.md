# Fixed decisions for the BEAM platform build

These decisions are made. Every spec, package and line of code follows them. Where a spec needs a choice that is not listed here, the spec makes the choice and records it; nothing is left "to be decided".

## Who builds it, and how

- Sidestream (Gaetan, Achile, one freelance developer) builds the platform with AI agents working in parallel. The build starts with a single overnight session that scaffolds the whole V1 and continues in weekly sprints.
- Timeline from the proposal: MVP in week 3, working V1 in week 6, go-live with real data in week 8, Releases 2–4 in weeks 9–14.
- BEAM owns the code (transferred to a BEAM-owned GitHub organisation), the data and every service account.

| Concern | Decision |

| Language | TypeScript everywhere, strict mode |
| Framework | Next.js 16 (App Router, React Server Components, Server Actions, Route Handlers). In Next.js 16 the request middleware file is `proxy.ts` (formerly `middleware.ts`) |
| Repo | pnpm workspace monorepo managed with Turborepo: `apps/*` and `packages/*` |
| Hosting | Vercel, Pro plan, functions pinned to `fra1` (Frankfurt). Vercel Cron for scheduled jobs |
| Database | Lakebase Postgres on Neon (PostgreSQL 18), project `lingering-waterfall-91843473`, org `org-fancy-meadow-65597173`, region `aws-eu-central-1` (Frankfurt), default branch `production`, with Neon branches for staging, preview and per-agent work. Drizzle ORM (`casing: snake_case`) with SQL migrations generated by drizzle-kit and committed in `packages/db/migrations` |
| Database driver | One Drizzle type for all code: `Db = PgDatabase<PgQueryResultHKT, typeof schema>` from `@beam/db`, with interactive transactions everywhere. Driver chosen by `DATABASE_DRIVER`: `pg` (default; `node-postgres` pool with `attachDatabasePool` from `@vercel/functions` on Vercel Fluid compute, Neon's recommendation for Vercel), `neon-ws` (`@neondatabase/serverless` Pool over WebSockets on port 443, same semantics as `pg`; used in the cloud build sandbox and CI where TCP 5432 is blocked) and `pglite` (`@electric-sql/pglite`, PostgreSQL 18 in-process; used by tests). App traffic uses the pooled `DATABASE_URL`; migrations use the direct `DATABASE_URL_UNPOOLED`. Neon's HTTP driver is not used because it has no interactive transactions |
| Databases | Neon project databases: `neondb` = production (untouched until go-live), `beam_dev` = development, demo and end-to-end tests during the build |
| Schema rules | No Postgres extensions required (PGlite parity): UUID keys via built-in `gen_random_uuid()`, case-insensitive email uniqueness via a unique index on `lower(email)`, no `citext`. Optional `pg_trgm` only behind a migration guarded for Neon |
| Jobs and queues | A Postgres-backed job table (`jobs`) processed by a Vercel Cron route every minute, plus event-driven triggers from server actions and webhooks. No external queue service in V1 |
| Email delivery | Resend (EU sending region), domains owned by BEAM: `mail.beam.be` transactional, `news.beam.be` marketing. Templates with `react-email`; marketing editor is block-based (JSON document → MJML → HTML) built in-house |
| Payments | Provider abstraction `PaymentProvider` with Mollie as the first adapter (Bancontact, cards, recurring mandates, payment links, terminal). Stripe and Viva adapters follow the same interface |
| Invoicing | Native invoices and credit notes in the platform; synced to Billit through its REST API. Billit remains the Peppol access point |
| Webinars | Video via YouTube Live (unlisted streams) embedded in the platform; registration, chat, polls, CTAs and watch-time tracking are native |
| AI | Anthropic Claude API through the official SDK. `claude-opus-5-5` for drafting and analysis, `claude-haiku-5-5` for classification and cheap tasks. No training on BEAM data; sensitive fields are excluded at the data layer |
| Auth | Two audiences: staff (email + password + TOTP MFA, role-based) and customers (passwordless magic link + optional password). Sessions in Postgres. Implemented with Auth.js v5 (next-auth) with the Drizzle adapter |
| i18n | `next-intl`. Three locales: `nl-BE`, `fr-BE`, `en`. Every user-facing string, email and form lives in a message catalogue; a missing translation blocks sending and falls back to showing the key in the admin UI |
| UI | Tailwind CSS v4 + shadcn/ui components; one shared `packages/ui` used by portal, website and back-office |
| Validation | Zod schemas shared between server actions, forms and API routes |
| Testing | Vitest everywhere. Integration tests get a fresh in-memory PGlite database per test file built straight from the TypeScript schema (`createTestDb()` from `@beam/db/testing`, which uses drizzle-kit's programmatic API), so parallel agents never share state, need no network and can test new tables before any migration exists. `createTestDb({ from: "migrations" })` proves the committed migrations. Playwright end-to-end tests run against `beam_dev` on Neon through the `neon-ws` driver |
| Observability | Sentry (EU region) for errors, Vercel Analytics and logs, Better Stack for uptime; alerts to a shared Slack channel |
| Timezone | All times stored in UTC; business logic uses `Europe/Brussels` |
| Money | Integer cents in `EUR`; VAT per line; prices snapshotted on every transaction |

## Existing foundation (already in the repo, verified working)

- pnpm 10 workspace + Turborepo; root scripts `build`, `dev`, `typecheck`, `db:generate`, `db:migrate`, `db:check`.
- `packages/db` (`@beam/db`): `getDb()` / `getDbHandle()` with the three drivers above, `checkDatabase()` health probe, `createTestDb()` for tests, empty `src/schema/index.ts` (every module adds its tables in its own file and re-exports them here), `drizzle.config.ts`, `scripts/migrate.ts` (works with both drivers), `migrations/` (empty journal).
- `apps/web` (`@beam/web`): Next.js 16 app with `app/api/health/route.ts` returning the database health; env loaded from the repo-root `.env.local`.
- `neon.ts` (Neon config as code, created by `neon init`) and `.neon` (project link, gitignored). Secrets live only in `.env.local` (gitignored); `.env.example` documents the variables.
- Verified on 2026-11-03: `npm run build` passes, `GET /api/health` returns 200 with a write/read round trip against Neon, `pnpm db:migrate` creates `drizzle.__drizzle_migrations`.
- In the cloud build sandbox, set `DATABASE_DRIVER=neon-ws NODE_USE_ENV_PROXY=1 NODE_EXTRA_CA_CERTS=/root/.ccr/ca-bundle.crt` for anything that talks to Neon. Tests use PGlite and need none of these. Wave 0 extends this foundation; it does not recreate it.

## Application layout

- `apps/web`: one Next.js app with three route groups: `(site)` public website, `(portal)` customer portal (installable PWA), `(admin)` staff back-office. One app keeps auth, i18n and deployment simple; route groups and middleware separate the audiences.
- `packages/db`: Drizzle schema, migrations, seed and query helpers.
- `packages/core`: domain logic (credits ledger, booking engine, pricing, automation engine, consent) with no framework dependency; unit-tested.
- `packages/email`: react-email templates, MJML renderer, Resend client.
- `packages/integrations`: Mollie, Billit, YouTube, Meta/Google Ads, Anthropic clients.
- `packages/ui`: shared components and design tokens.
- `packages/config`: eslint, tsconfig, tailwind presets.

## Architecture principles

1. One central `persons` record. Every module reads and writes it; nothing else stores customer identity.
2. Append-only facts: `activity_events` (timeline), `credit_entries` (ledger), `consent_records`, `audit_log`, `automation_runs`. Balances and statuses are derived, never edited by hand.
3. Versioned definitions: forms, assessments, prices, email templates and terms. History always points to the version that produced it.
4. Rules before AI. Retention lists, package thresholds, waitlists and automations are deterministic.
5. Sensitive fields (health, sleep, stress, recovery) are tagged in the schema, restricted by role, excluded from AI and exports by default.
6. Every outbound side effect (email, payment call, Billit sync, webhook) goes through the `jobs` table with retries and alerts on failure.
7. Config, not code: schedules, capacities, prices, promotions, sequences, roles and dashboards are editable by BEAM staff.
8. No multi-tenancy. The platform is single-tenant and config-driven; a second deployment serves a second client.
9. Feature flags per user let new features ship to test users on production before everyone sees them.
10. Deletion and export are first-class workflows that reach every table and connected service.

## Parallel build rules (how many agents build this at once without collisions)

1. **One owner per file.** Every build package lists the files it creates or edits; no two packages in the same wave touch the same file.
2. **No dependency changes inside packages.** Wave 0 installs every npm dependency the whole platform needs. A package that needs something else writes it to `docs/build/dependency-requests/<package-id>.md` (one file per package); the orchestrator adds it between waves.
3. **No migrations inside packages.** Packages only edit Drizzle schema files (`packages/db/src/schema/<module>.ts`). After each wave is merged, the orchestrator runs `pnpm db:generate` once, commits the migration, and the gate runs `pnpm db:check-migrations`.
4. **Registries by convention, indexes generated.** Shared lists (schema re-exports, job handlers, permissions, activity event types, navigation, i18n message namespaces, route registries) live in one file per module; a generator script (`pnpm gen:indexes`) writes the index files. Packages never edit generated index files by hand.
5. **Worktree per package.** Each coding agent works in its own git worktree on branch `build/<package-id>`, runs `pnpm install --offline` (shared pnpm store), and must leave `pnpm typecheck` and its own Vitest suites green before it commits.
6. **Wave gate.** After merging a wave: `pnpm gen:indexes`, `pnpm db:generate`, `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`, and at checkpoints Playwright against `beam_dev`. A red gate is fixed before the next wave starts.
