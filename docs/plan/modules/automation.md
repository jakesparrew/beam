# Module spec: automation (Automation engine and journeys)

Owner module id: `automation`. Blueprint sections 20, 21, 31, 51, with requirements also taken from sections 5, 6, 11, 12, 17, 18, 19, 22, 29, 30, 37, 47, 48, 53, 56, 62, 72, 76, 80 and 87. This spec follows `docs/plan/00-decisions.md` and `docs/plan/01-architecture.md` (section 7 is the engine contract). Everything below is decided.

## 1. Purpose and release mapping

The automation module turns facts into follow-up. It reads `activity_events`, enrols people into journeys, plans every step from the enrolment or from an anchor (a webinar start, a session start, an offer expiry), checks everything again at send time, and writes one append-only log row for every decision. It never sends email itself; it hands messages to the `email` module and tasks to `crm`. Rules come before AI: no step in this module calls Claude.

| Release | What ships in this module |
| --- | --- |
| **V1 (weeks 1-6)** | Tables, views and the JSON definition format with all 12 step types (`email`, `wait`, `condition`, `task`, `tag`, `untag`, `set_field`, `status_override`, `enrol`, `exit`, `notify_slack`, `webhook`). Triggers by event with `where` filter, `segment_enter` and `manual`. Evaluator job every minute with gap-safe cursor; enrolment under a person row lock; audience, re-entry and exit rules; exclusive groups with priority (engine rule, seeded groups); late-entry skip at enrolment (scenario 1); send-time re-evaluation; pause and resume; versioning with optional migration; `automation.exit_for_suppression` (scenario 2). Staff controls on the person page (exit, enrol, move, preview, timeline). Admin screens: list, detail, form-based step editor with a JSON tab, versions, enrolments, run log. Seeded editable sequences: `welcome-lead`, `lead-sales-follow-up`, `assessment-follow-up`, `event-registration`, `after-first-booking`, `after-first-visit`, `package-usage`, `package-expiry` (packages and gift vouchers), `package-finished`, `inactivity` (30, 60, 90 and 180 days), `member-welcome`, `membership-renewal`, `review-request`, `waitlist-offer`. Seeded as `draft` for later activation: `abandoned-checkout`, `waitlist-follow-up`, `event-follow-up` and every webinar journey (section 3.6). Import guard: imported history never enrols anyone, and a definition triggered by `ops.history_imported` cannot be published (A-1, A-7). Monitoring for the SLA: dead step jobs, stuck enrolments and evaluator lag alert Slack within 15 minutes (A-35, A-45). |
| **Release 2 (weeks 9-10)** | "Automation conflict rules" as BEAM-editable configuration: group editor (exclusive, lane, priority), frequency caps and quiet hours for marketing steps (`settings.automation_rules`), the conflict report. ## 2. Domain model

Schema file `packages/db/src/schema/automation.ts`, views in `packages/db/src/schema/automation.views.ts`. Conventions from architecture section 2: uuid keys with `gen_random_uuid()`, `created_at timestamptz not null default now()`, `updated_at` on mutable tables, enums `pgEnum('<table>_<column>')`. No column in this module is sensitive in the Article 9 sense; columns holding personal data are marked **PD**. Events with `activity_events.is_sensitive = true` never trigger, exit or enter context (rule A-7), so no sensitive value can reach these tables.

### 2.7 Views (`automation.views.ts`, Drizzle `pgView` with `.as(sql)`)

```sql
create view v_automation_stats as
with e as (select automation_id,
             count(*) filter (where status = 'active')    as active_count,
             count(*) filter (where status = 'completed') as completed_count,
             count(*) filter (where status = 'exited')    as exited_count,
             count(*) filter (where entered_at > now() - interval '7 days') as entered_7d
           from automation_enrolments group by automation_id),
     r as (select automation_id,
             count(*) filter (where outcome = 'sent')        as sent_7d,
             count(*) filter (where outcome::text like 'skipped_%') as skipped_7d,
             count(*) filter (where outcome = 'failed')      as failed_7d,
             max(occurred_at) as last_run_at
           from automation_runs where occurred_at > now() - interval '7 days' group by automation_id)
select a.id as automation_id, a.slug, a.status,
       coalesce(e.active_count,0) active_count, coalesce(e.completed_count,0) completed_count,
       coalesce(e.exited_count,0) exited_count, coalesce(e.entered_7d,0) entered_7d,
       coalesce(r.sent_7d,0) sent_7d, coalesce(r.skipped_7d,0) skipped_7d,
       coalesce(r.failed_7d,0) failed_7d, r.last_run_at
from automations a left join e on e.automation_id = a.id left join r on r.automation_id = a.id;

create view v_automation_due as
select en.id as enrolment_id, en.automation_id, en.person_id, en.next_step_key, en.next_step_at
from automation_enrolments en join automations a on a.id = en.automation_id
where en.status = 'active' and a.status = 'active' and en.next_step_at <= now();

create view v_person_automation_timeline as
select r.id, r.person_id, r.occurred_at, r.outcome, r.step_key, r.reason, r.enrolment_id,
       a.slug as automation_slug, a.name as automation_name, en.end_reason,
       r.email_message_id, m.status as email_status, r.task_id
from automation_runs r join automations a on a.id = r.automation_id
left join automation_enrolments en on en.id = r.enrolment_id
left join email_messages m on m.id = r.email_message_id;
```

### 2.8 The definition (`packages/core/src/automation/definition.ts`, Zod)

```ts
type Definition = {
  schema_version: 1;
  trigger: { event: string | string[] /* any of these kinds */; where?: Filter } | { segment_enter: string /* segment uuid */ } | { manual: true };
  anchor: 'enrolment' | `data.${string}`;           // path into the trigger event data, ISO timestamp
  subject?: 'ref';                                   // one enrolment per trigger ref_type:ref_id
  audience?: { status?: ('lead'|'customer'|'member')[]; segment_id?: string; exclude_segment_ids?: string[];
               locales?: ('nl-BE'|'fr-BE'|'en')[]; require_reachable?: boolean /* default = is_marketing */ };
  re_entry: 'never' | 'always' | `after_days:${number}`;
  exit_on: (string | { event: string; where?: Filter; same_subject?: boolean })[]; // "kind" or "kind:qualifier"
  steps: Step[];                                     // 1..40 steps, keys unique, ^[a-z0-9_]{1,40}$
};
type At = { from: 'enrolment' | 'anchor' | 'previous'; minutes: number; snap_to?: `${number}:${number}` /* HH:mm Brussels */ };
type StepBase = { key: string; at?: At; unless?: Condition; late_entry?: 'skip' | 'send_now' };
type Step = StepBase & (
  | { type: 'email'; template: string /* email_templates.slug */ }
  | { type: 'wait'; minutes: number }
  | { type: 'condition'; if: Condition; then: string | 'end'; else: string | 'end' }   // forward targets only
  | { type: 'task'; title: string; kind: 'call'|'follow_up'|'payment'|'proposal'|'review'|'other';
      owner_role: string; due_in_minutes: number; priority: 'low'|'normal'|'high';
      owner?: 'role' | 'trigger_owner' /* default role; trigger_owner = data.owner_user_id of the trigger (R3 B2B) */ }
  | { type: 'tag' | 'untag'; tag: string /* tags.key */ }
  | { type: 'set_field'; field: 'preferred_channel'; value: 'email'|'phone'|'whatsapp' }   // written through crm.updatePersonFields
  | { type: 'status_override'; value: 'lead'|'customer'|'member'|null; reason: string }
  | { type: 'enrol'; automation: string /* slug */ }
  | { type: 'exit'; automation?: string /* slug; omitted = this enrolment */ }
  | { type: 'notify_slack'; text: string /* placeholders {{first_name}} {{person_url}} {{automation}} only */ }
  | { type: 'webhook'; url: string /* https, host in settings.automation_rules.webhook_hosts */ } );
type Filter = Record<string /* dotted path: data.x, mode, ref_type */, Literal | { eq?; ne?; in?; nin?; gt?; gte?; lt?; lte?; exists?: boolean }>;
type Condition =
  | { all: Condition[] } | { any: Condition[] } | { not: Condition }
  | { has_future_booking: true | { kind?: 'day'|'night'|'event'; within_days?: number } }
  | { status_in: ('lead'|'customer'|'member')[] } | { has_tag: string } | { in_segment: string }
  | { has_active_membership: true } | { membership_cancelling: true }
  | { has_other_active_grant: { credit_kind: 'day'|'night'|'euro' | '{{trigger.data.credit_kind}}' } }
  | { form_completed: { slug: string; within_days?: number } }      // a completed submission of that form exists
  | { processing_restricted: true }                                  // persons.processing_restricted_at is not null (crm)
  | { event_since_enrolment: string /* kind */ } | { booking_status_in: ('attended'|'no_show'|'confirmed'|'cancelled')[] /* trigger booking */ }
  | { trigger: Filter /* matches the trigger event */ } | { task_open: string /* step key of a task step */ }
  | { sent_within_days: { template: string; days: number } };
```

`Literal` is string, number, boolean or null. `{{trigger.data.x}}` interpolation is allowed only inside `has_other_active_grant.credit_kind` and as a literal value inside an `exit_on` object's `where` (resolved against `context.trigger.data` of the enrolment being checked, so `package-usage` exits on `credits.granted` of the same `credit_kind`), and as `{{trigger.data.<key>}}` inside a `task.title` for a string key of the trigger data (used by `webinar-cta-sales-task` for `cta_key`, cross-module D52). The parser rejects unknown keys (`.strict()`). The architecture's example writes `"audience": { "segment": ... }` and `"group": ...` inside the definition; here the audience segment is `audience.segment_id` (a uuid, so renaming a segment never breaks a journey) and the group lives on `automations.group_id` (so moving a journey between groups needs no new version). Both are recorded in section 13.

## 3. Business rules

Each rule has an id used by tests (`it('A-12 ...')`).

### 3.1 Definitions, versions and status

- **A-1** A definition is valid only if `AutomationDefinition.parse` succeeds and `validateDefinition` returns no issues: step keys unique; `condition.then/else` point to a later step or `end` (no loops); every `email.template` is a published template; every `enrol`/`exit` slug exists and is not the automation itself for `enrol`; every `tag` key exists; `owner_role` is a seeded role key; `webhook.url` is `https` and its host is in `settings.automation_rules.webhook_hosts`; anchor-relative `at` requires `anchor <> 'enrolment'`; an exclusive-group automation must not set `subject`; the trigger kind (or any kind of a trigger list) must not be `ops.history_imported` (issue `trigger_history_imported`, ops rule 47b: imported history is a fact about the past and never starts a journey), nor a kind starting with `automation.`.
- **A-2** Publishing inserts `automation_versions.version = max + 1` with the draft, sets `current_version_id`, and is refused (`conflict`) when `definition_hash` equals the current version's hash. Published versions are never edited or deleted.
- **A-3** Publish-time translation check: every template referenced by an `email` step must have a published version whose `locales` contain every locale in `audience.locales` (default all three). Missing locales fail the publish with the list (`assertComplete` semantics).
- **A-4** A marketing step (template `kind = marketing`) inside an automation with `is_marketing = false` is allowed; its reachability is still checked per step (A-31). When the automation has a `purpose`, a `marketing` template whose `purpose` differs from it fails validation; when the automation `purpose` is null (transactional automations such as `after-first-visit`), any marketing template is accepted and its own purpose decides reachability.
- **A-5** Status moves: `draft -> active` (activate, needs a published version), `active <-> paused`, `draft|active|paused -> archived`. Every other move (`draft -> paused`, `paused -> draft`, `archived -> *`) returns `conflict`. Archiving exits all active enrolments with reason `archived`. An archived automation cannot be reactivated; staff duplicate it instead (the duplicate copies `requires_dpia` and `requires_flag`). Each status action locks the `automations` row `FOR UPDATE`, so a double click or two staff members cannot interleave a pause and an archive.
- **A-5a** DPIA gate (blueprint 66, webinar 4.8): `draft -> active` and `paused -> active` are refused with `conflict` (issue `dpia_not_approved:<key>`) while `requires_dpia` is set and `ops.isDpiaApproved(db, requires_dpia)` is false; `activateReleaseSequences` skips such journeys and reports them. The seed sets `requires_dpia = 'watch_time_profiling'` on every webinar journey that acts on watch thresholds, attendance or CTA clicks (`webinar-attended`, `webinar-watched-15`, `webinar-watched-30`, `webinar-watched-end`, `webinar-replay`, `webinar-on-demand`, `webinar-cta-click`, `webinar-cta-sales-task`; cross-module D52); `webinar-registration`, `webinar-no-show` and `webinar-poll-answer` carry none. The evaluator re-checks the gate once per run for active gated automations (one `isDpiaApproved` call per key per run): when the decision is no longer approved, those automations are paused by the system (audit `automation.pause` with actor `system`, Slack `normal` fingerprint `automation-dpia:<key>`).
- **A-6** New enrolments always use `current_version_id`. Existing enrolments keep their version unless staff tick "migrate active enrolments" on publish (A-40).

### 3.2 Evaluation and enrolment

- **A-7** The evaluator ignores events with `is_sensitive = true` and events whose kind starts with `automation.`; such events never trigger, exit or enter `context`. Three more classes of event may exit enrolments but never trigger one: (a) imported history, `data.source = 'import'` or `data.via_import = true` (crm, booking, webinar and forms mark imported facts this way), and every `ops.history_imported` event (ops writes past purchases and visits to `imported_history` with that event; no definition can be published with it as a trigger, A-1, and the evaluator never matches it as a trigger even in a definition published before the rule), so the week-7 data migration enrols nobody; (b) events whose `occurred_at` is more than 48 hours before the evaluation time (a backfill or a late correction never sends "welcome" for an old fact); (c) events produced by an automation step, `data.source = 'automation'` (crm's `tag.added`, `task.created`, `person.status_overridden` from an automation write it), so a tag step cannot start a loop.
- **A-8** The evaluator processes events in `id` order after `settings.automation_cursor.last_event_id`, at most 1,000 events per job run read in pages of 250, within 30 seconds. The run is one transaction (the job contract gives each run one transaction); each event is processed inside a savepoint (`tx.transaction(...)`), so an event whose processing throws is rolled back alone, logged (A-46) and skipped. When more events remain, the run enqueues a continuation `automation.evaluate` with key `automation_evaluate:<last_event_id>` on the fast lane, which the same tick picks up. It also re-reads ids listed as gaps in the cursor (ids between processed ids that were not visible yet); a gap older than 10 minutes is dropped (rolled-back transaction). Re-reading is harmless because of `uq_enrolment_trigger` and A-22's exit guard.
- **A-9** Per event the order is fixed: (1) built-in exits, (2) `exit_on` matches of that person's active enrolments, (3) trigger matches of `active` automations sorted by group priority, then automation priority, then slug. A purchase therefore ends lead nurture before the customer journey is considered.
- **A-10** A trigger matches when the kind is equal and every `where` path matches (`eq` for literals, operators as declared; a missing path fails every operator except `exists: false`). `segment_enter` matches `segment.entered` with `data.segment_id` equal. `manual` never matches an event.
- **A-11** Enrolment runs inside one transaction holding `SELECT id FROM persons WHERE id = $1 FOR UPDATE`. A person with `erased_at` or `merged_into_person_id` set is never enrolled. A person with `persons.processing_restricted_at is not null` (GDPR restriction or objection; set and cleared by `crm.restrictProcessing`, the one restriction flag) is never enrolled into a marketing automation (`is_marketing = true`); the run `skipped_unreachable` with reason `restricted` is written. Transactional journeys (bookings, payments, waitlist) continue, as ops rule 65 requires.
- **A-11a** Flag gate: an automation with `requires_flag` set is skipped at trigger matching while `flag(requires_flag, ctx.actor)` is off (the job's `{ kind: 'system', jobId }` actor, so only the flag's global `on` state counts, never a tester list) (no run row, like a failed audience check), and at step time a due step of such an automation writes `skipped_condition` with reason `flag_off:<key>` and the enrolment advances. `abandoned-checkout` is seeded with `requires_flag = 'ff_commerce_checkout_recovery'` (commerce rule 52).
- **A-12** Audience check at entry: `status` against `v_person_status`, `segment_id` and `exclude_segment_ids` against `segment_members`, `locales` against `persons.locale`. A failed audience check writes no run row (it is not a journey decision, and logging it would flood the log).
- **A-13** Re-entry is judged per person across all subjects of the automation: `never` refuses if any enrolment of this automation exists for the person; `after_days:N` refuses if the person's latest `entered_at` in this automation is less than N days ago (so `review-request` with a per-booking subject still sends at most one request per 30 days); `after_days:0` and `always` allow. Independently, an active enrolment for the same automation, person and subject always refuses the new one (`uq_enrolment_active`).
- **A-14** Marketing entry check: when `require_reachable` (default `is_marketing`) is true, `v_marketing_reachability` must be reachable for the automation `purpose`; otherwise the run `skipped_unreachable` is written with `enrolment_id` null and nothing is enrolled.
- **A-15** Exclusivity: for an exclusive group, if no active enrolment exists in the domain, enrol. If one exists and the candidate has a lower `(group.priority, automation.priority)` pair, the existing enrolment exits with `superseded` (run `exited`, `data.superseded_by`) and the candidate enrols. Otherwise the candidate writes `skipped_exclusive` (reason names the blocking automation) and does not enrol. Equal pairs keep the existing enrolment. `uq_enrolment_domain` enforces the result.
- **A-16** The anchor is read from the trigger event path (ISO timestamp). A missing or unparsable anchor writes `failed` with reason `anchor_missing` and no enrolment. An anchor already in the past at entry is allowed; steps planned before entry are skipped (A-18). If every step would be skipped, the enrolment completes at once with `end_reason = anchor_passed`.
- **A-17** `planSteps` computes `due_at` per step along the default path: `from: enrolment` = `entered_at + minutes`; `from: anchor` = `anchor_at + minutes`; `from: previous` or no `at` = due of the previous planned step that is not skipped (or `entered_at`) plus any `wait` minutes in between; `snap_to` sets the Brussels local time on that date (DST-safe). A step after a `condition` is planned on the default path and re-planned when the branch is taken.
- **A-18** Late-entry skip (scenario 1): at enrolment every step with an `at` of `from: enrolment|anchor` whose `due_at < entered_at` gets `skipped_late_entry` with `data.due_at`, unless the step has `late_entry: send_now`, in which case it becomes due at `entered_at`. Steps relative to the previous step are never late. A Friday 10:00 registration for a Sunday 10:00 event in `event-registration` logs `skipped_late_entry` for `reminder_7d` and `reminder_3d` and keeps `reminder_day_of`; the confirmation itself is booking's `booking.booking_confirmed` email sent in the booking transaction, so the person receives exactly the confirmation and the day-of reminder (scenario 1).
- **A-19** After planning, the run `entered` (with `data.trigger_event_id`) and one `scheduled` row for the first pending step (with `data.due_at`) are written; `next_step_key` and `next_step_at` are set.
- **A-20** The evaluator enqueues `automation.step` for every row of `v_automation_due` (at most 500 per run, oldest first). The job key `automation:<enrolment_id>:<step_key>` makes double enqueueing harmless.

### 3.3 Exits

- **A-21** Built-in exits apply to every automation regardless of `exit_on`: `person.merged` for the loser (reason `merged`), `suppression.added` (marketing automations whose purpose is in scope, reason `unsubscribed`), `consent.withdrawn` with `data.purpose` equal to the automation purpose (reason `consent_withdrawn:<purpose>`), and for marketing automations `privacy.restricted` (reason `restricted`) and `privacy.objected` (reason `objected`). Erasure emits no event (ops deletes the timeline), so it ends enrolments through the direct call `exitPersonEnrolments(..., 'erased')` from automation's own `privacy.erase` handler; restriction and objection also call `exitAllForPerson` directly in ops's transaction, and the events are the safety net.
- **A-22** `exit_on` entries: `"kind"` matches the kind; `"kind:q"` also needs `data.purpose = q` or `data.scope = q` or one of `data.lines[].kind = q` (commerce's `order.paid`); the object form adds `where` and `same_subject` (event `ref_type:ref_id` equals `subject_key`). Matching enrolments end `exited` with `exit_event:<kind>`. Guard: an event only exits enrolments whose `trigger_event_id` is null or lower than the event id, so an event never ends the enrolment it created itself (on a gap re-read or a retry) and an `exit_on` that names the trigger kind (`package-usage`) ends only the older enrolment.
- **A-23** `automation.exit_for_suppression` (scenario 2) loads the suppression, finds persons by `persons.email_hash = suppressions.email_hash` through crm's `findPersonIdsByEmailHash(tx, emailHash)` (an index lookup on `persons_email_hash_idx`; it includes merged rows, whose enrolments already ended `merged`; an erased person has a null hash and nothing to end), and in one transaction ends every active enrolment of a marketing automation whose purpose is covered by the scope (`all` covers every purpose) with `unsubscribed`. It runs in the `after()` kick of the suppressing action, so marketing journeys end within seconds; the per-minute evaluator and the send-time check are the safety nets, well inside 15 minutes.
- **A-24** Transactional automations (`is_marketing = false`) are not exited by suppressions or consent withdrawal; their marketing steps are still skipped by A-31.
- **A-25** Ending an enrolment sets `status`, `ended_at`, `end_reason`, clears `next_step_*`, marks pending plan entries `not_taken`, and writes exactly one `exited` or `completed` run. Pending `automation.step` jobs find the enrolment ended and finish as no-ops.

### 3.4 Step execution (send-time re-evaluation)

- **A-26** `automation.step` locks the enrolment `FOR UPDATE` and checks in this order, writing one run row for the first failing check: enrolment active and `next_step_key` equals the job's step (else no-op, no row); automation not `paused` (no row; the job succeeds without effect and the step stays due, re-enqueued on resume by A-29); person not erased (exit `erased`); overdue rule A-28; `unless` true (`skipped_condition`, reason `unless:<predicate>`); step-specific checks A-31 to A-33.
- **A-26a** Job keys. The evaluator always enqueues a due step with the architecture key `automation:<enrolment_id>:<step_key>`, so repeated evaluator passes never double-enqueue. Because a succeeded job row keeps its key for 7 days, a step that must run again later (paused in the race between enqueue and run, or deferred by quiet hours) is re-enqueued with a qualified key: `automation:<enrolment_id>:<step_key>:resume:<resumed_at ms>` (A-29) or `automation:<enrolment_id>:<step_key>:defer:<run_at ms>` (A-32), with `runAt` set. The email idempotency key stays `automation:<enrolment_id>:<step_key>`, so a step sends at most one email whatever the number of job attempts.
- **A-27** Conditions are evaluated against fresh facts loaded at step time inside the job transaction (`loadFacts`), never against values copied at entry.
- **A-27a** Anchor refresh: for an enrolment with subject `booking:<id>` and anchor `data.starts_at`, the step job compares `anchor_at` with the booking's current session `starts_at` before an anchor-relative step; a difference above 5 minutes updates `anchor_at`, re-plans pending steps with A-17 and A-18 (reason `anchor_moved`) and ends the run without sending (edge case 10b).
- **A-28** Overdue rule: an `email`, `notify_slack` or `webhook` step processed more than 24 hours after `due_at` is skipped: `skipped_paused` when the automation was paused during that window, else `skipped_stale`. `task`, `tag`, `untag`, `set_field`, `status_override`, `enrol` and `exit` steps still run late.
- **A-29** On resume, `automation.resume_enrolments` writes `skipped_paused` for every active enrolment whose `next_step_at` is more than 24 hours before the resume time and whose step is time-sensitive (A-28) and advances them; for every other enrolment already due it enqueues `automation.step` with the `:resume:` key of A-26a; enrolments due later run normally through the evaluator.
- **A-30** `has_future_booking` is true when `v_person_bookings` has a booking in status `reserved|confirmed` with `starts_at > now()` (optionally filtered by kind and `within_days`). Inactivity steps use it so nobody with a relevant booking gets "we miss you".
- **A-31** Email step: resolve the template with `email.getPublishedTemplateInfo(tx, [slug])` (current published version, kind, purpose, locales; absent = `failed` with reason `template_unavailable`); for a marketing template require `email.getReachability(tx, personId, purpose).isReachable` (the same rule as `v_marketing_reachability`; `skipped_unreachable` with the `blockedReason`); require `persons.locale` in the version's `locales` (`skipped_translation`, counted for the daily digest and alerted by A-45); then call email's function for the template kind returned by `getPublishedTemplateInfo(tx, [slug])`: `email.queueMarketingEmail(ctx, input)` for a `marketing` template and `email.queueAutomationEmail(ctx, input)` for a `transactional` one (cross-module D7; `ctx` carries the step job's transaction as `ctx.tx`), with `input: AutomationEmailInput = { templateSlug, personId, enrolmentId, idempotencyKey: 'automation:<enrolment_id>:<step_key>', context, stepKey }` (email applies consent for marketing templates and suppression scope `all` for transactional ones). One exception (cross-module D54): the steps of `abandoned-checkout` send the transactional registry template `commerce.checkout_recovery` through `queueMarketingEmail` as a marketing message, with the automation's purpose `newsletter` for reachability. `context` and `stepKey` are always passed (`stepKey` lets a template such as `webinar.reminder` pick its variant), `context` is built by `buildEmailContext(enrolment)`: the string ids of `context.trigger` (`ref_type`, `ref_id`, and every `data` key ending in `_id`), `subject_key`, `enrolment_id`, and for `abandoned-checkout` the `checkout_id` and `resume_url` from `commerce.getCheckoutRecoveryProps(tx, checkoutId)` (A-31a), so email never has to read `automation_enrolments.context`. The result is `{ messageId, status: 'queued' | 'skipped_unreachable' | 'skipped_translation', created, templateVersionId }`; the run outcome equals the returned status (`sent` for `queued`, with `email_message_id = messageId` and `data.template_version_id`; `skipped_unreachable` and `skipped_translation` are passed through unchanged, because email repeats the checks). `email.send` checks suppressions once more before Resend.
- **A-31a** Checkout recovery (R2, commerce rules 51 and 52): an email step in an enrolment with subject `checkout:<id>` calls `commerce.getCheckoutRecoveryProps(tx, checkoutId)` before queueing (it creates the resume token once; `resumeUrl` goes into `context.resume_url`), and after a `queued` result calls `commerce.markCheckoutRecoveryMessage(tx, { checkoutId, emailMessageId })` (`emailMessageId` = the returned `messageId`) in the same transaction (commerce sets it only while null, so the first recovery email is the attributed one). Exits on `checkout.completed` and `order.paid` end the journey before the next step.
- **A-32** Frequency cap (R2, marketing templates only): more than `max_marketing_per_day` (default 1) or `max_marketing_per_week` (default 3) automation marketing emails to the person in the trailing window gives `skipped_frequency_cap`. Quiet hours (default 21:00-08:00 Brussels) move a due marketing email to 08:00 the next morning instead of skipping: the job writes a new `scheduled` row, sets `next_step_at`, and enqueues itself with the `:defer:` key and `runAt` (A-26a). Transactional templates are never capped or deferred.
- **A-33** Other steps: `task` creates a `crm` task through `crm.createTask` (`source: 'automation'`, `ref: { type: 'automation_enrolment', id: enrolmentId }`, `dedupeKey: 'automation:<enrolment_id>:<step_key>'`; crm's signature, cross-module D14) owned by the active staff user returned by `platform.listStaffForAssignment(tx, { roleKey: owner_role })` with the fewest open tasks (ties by name), or with `owner: trigger_owner` by the trigger's `data.owner_user_id` when that user is active; due `now + due_in_minutes`, then moved forward to the next opening time from `booking.nextOpeningAt(tx, due, { includePublicHolidays: true })` (it returns `Date | null`; on `null` the computed due time is kept) (weekly `settings.business_hours` plus booking's closed-day and holiday exceptions), so no task falls due on a Sunday the centre is closed or on a Belgian public holiday -> `task_created`; `tag`/`untag` -> `tag_applied`/`tag_removed` (no row change if already in that state, still logged); `set_field` -> `field_set`, written through `crm.updatePersonFields(tx, ctx, personId, { preferredChannel: value }, { onlyEmpty: false })` (crm's `PersonFieldPatch` field, cross-module D13) (an unchanged value is still logged); `status_override` -> `status_set` with the reason, written through `crm.setStatusOverride`; `enrol` enrols into the target (all entry rules apply, source `enrol_step`) -> `enrolled` or the target's skip row; `exit` ends this or the named enrolment -> `exited` with `exit_step`; `notify_slack` calls `platform.notifySlack(ctx, { fingerprint, severity: 'normal', text })` -> `notified`; `webhook` enqueues `automation.call_webhook` and the enrolment advances at once (fire and forget); that job writes `webhook_called` on 2xx, and its `onDead` hook writes `failed` when it is dead (A-35).
- **A-34** After a step, the next step is the `then`/`else` target for a condition (run `branched` with `data.result` and `data.target`), else the next planned step that is not skipped. The next step is re-planned if its due was computed on the other branch. No next step: `completed`.
- **A-35** A step job that throws a `RetryableError` retries with the platform backoff (60 s to 6 h). `automation.step` and `automation.call_webhook` declare platform's `onDead(ctx, input, error)` hook (PL-29a), implemented once as `recordDeadStep(ctx, input: { enrolmentId, stepKey }, error: { message, permanent })`: in the hook's own transaction it locks the enrolment, writes one `failed` run (reason = `error.message`, first 200 characters, prefixed `permanent:` when `error.permanent`; `dedupe_key run:<enrolment_id>:<step_key>:failed`) and advances a still-active enrolment whose `next_step_key` is that step (for `call_webhook` the enrolment already advanced, so only the run is written). The hook never throws for a missing or ended enrolment (no-op). Fallback: when the hook itself threw (the job stays `dead` without a `failed` run, platform edge case 32), `automation.sweep_enrolments` (every 15 minutes) reads `dead` jobs of those two kinds from the last 7 days and calls the same `recordDeadStep`; the dedupe key makes the two paths write one row. The platform alerts every dead job in Slack and on `/admin/system/jobs`. A staff Retry of a dead step job is harmless: the step re-checks state, the email key prevents a second send, and a second dead transition calls the hook again, which writes nothing new.
- **A-44** Protected facts: no step type creates, changes or cancels a booking, a waitlist entry, a credit entry, an order or a payment. Automations can only send, tag, create tasks, set the preferred channel or a status override, enrol, exit, notify and call a webhook. A confirmed seat can therefore never be removed by an automation (scenario 4, acceptance "confirmed seat is protected").
- **A-45** Health signals (SLA High: "emails not sending"). This module owns the "Failed automations" check of platform's PL-75a (platform owns the mechanism and the dead-job alert of PL-29; the check, its thresholds and its fingerprints are here). The sweep alerts through `platform.notifySlack(ctx, ...)` with severity `high` when (a) any enrolment of an active automation is more than 30 minutes past `next_step_at` (fingerprint `automation-stuck`), (b) the evaluator lags, meaning the oldest unprocessed `activity_events` row is more than 5 minutes old (fingerprint `automation-lag`), or (c) more than 20 `failed` runs were written in the last hour (fingerprint `automation-failures`). `skipped_translation` rows alert with severity `normal` once per template per hour (fingerprint `automation-translation:<template_slug>`). `countAutomationIssues` returns the same numbers for the daily digest and the System page. Platform's alert table (PL-75a) names automation as the check owner for dead `automation.step` jobs (failed runs from `onDead`, A-35), `automation_runs.outcome = failed` (c) and stuck enrolments (a).
- **A-46** An event whose processing throws in the evaluator writes a `failed` run (reason `evaluate:<message>`, `dedupe_key entry:<automation_id>:<event_id>`) for the automation being matched, and the cursor moves on. One bad definition cannot stall every journey.

### 3.5 Staff controls, preview and timeline

- **A-36** Exit (person page): ends one active enrolment with `manual`; needs `automations.move_person`; one audit row `automation.person_exit`.
- **A-37** Enrol: staff enrol a person into any `active` automation; re-entry and exclusivity priority are overridden (a blocking enrolment in the domain exits with `moved`), the audience mismatch is shown as a warning but allowed, the anchor must be given when the definition has a data anchor, marketing reachability is still enforced per step. Audit `automation.person_enrol`.
- **A-38** Move: exit one enrolment (`moved`) and enrol into another automation in one transaction and one audit row `automation.person_move` with old and new automation slugs. Both appear on the timeline.
- **A-39** Preview: `previewEnrolment` runs `planSteps` and the step checks read-only and returns each step with `due_at` and the predicted outcome (`will_send`, `late_entry`, `condition_false`, `unreachable`, `translation_missing`, `frequency_cap`). It writes nothing.
- **A-40** Migration on publish (`automation.migrate_enrolments`, bulk lane, 500 per chunk): each active enrolment of older versions exits `migrated` and a new enrolment with the same anchor, subject, context and `migrated_from_enrolment_id` (source `migration`, `trigger_event_id` null) enters the new version; exclusivity is not re-judged (the old enrolment held the domain slot and releases it in the same savepoint). Steps whose key was already executed in the old enrolment are marked `done` without a run; other steps planned before now get `skipped_late_entry` with reason `migrated`.
- **A-41** The person timeline shows every run row with automation name, step, outcome, reason and email status, newest first; the blueprint list "entered, trigger, step, skipped step, condition, branch, exit, exit reason" maps to `entered` (+ `data.trigger_event_id`), `sent`/`task_created`/..., `skipped_*`, `branched`, `exited` + `end_reason`.

### 3.7 B2C pipeline (Release 2)

- **A-42** The stage is computed by `ops` (`person_stats.b2c_stage`), never typed. Automations drive stage changes by producing the facts the stage rule reads: tag `engaged` (applied by `welcome-lead` on a click, by webinar journeys on 15 minutes watched) makes a lead `engaged_lead`; bookings, attendance and orders do the rest. `ops` emits `ops.stage_changed { from, to }` (ops rule 14, dedupe once per stage per day) when the nightly or on-demand refresh changes it.
- **A-43** Each stage of blueprint 20 has one seeded playbook automation (blueprint 29: required action, owner, deadline, automated and human communication, escalation): `engaged_lead` -> task "Nodig uit voor BEAM Experience" sales, 2 d, escalation `notify_slack` after 4 d if `task_open`; `experienced` -> task "Plan eerste bezoek" sales 2 d; `first_visit` -> handled by `after-first-visit`; `first_purchase` -> task "Welkomstgesprek" customer_service 3 d; `repeat` -> tag `repeat`; `member` -> exit step for `welcome-lead` and `after-first-visit`; `retention` -> task "Reactiveringscall" customer_service 2 d, escalation after 5 d; `lost` -> tag `lost`. KPIs per stage are reported by `ops`.

## 9. Privacy

`apps/web/modules/automation/privacy.ts` registers into `GDPR_REGISTRY`:

```ts
export const automationPrivacy = {
  tables: ['automation_enrolments', 'automation_runs'],
  export: (tx, personId) => /* { enrolments: [...], runs: [...] } */,
  erase: (tx, personId) => /* [{ table, rows, action }] */,
  sweep: {
    'automation.automation_runs': (tx, cutoff) => purgeAutomationHistory(tx, 'automation.automation_runs', cutoff),
    'automation.automation_enrolments': (tx, cutoff) => purgeAutomationHistory(tx, 'automation.automation_enrolments', cutoff),
  },
};
```

| Table | Person data | Export includes | Erase does | Why |
| --- | --- | --- | --- | --- |
| `automation_enrolments` | `person_id`, `context` (trigger event data), `subject_key` | automation slug and name, version, status, entered, ended, end reason, anchor, plan (keys, due times, states), context | **deleted** (after `exitPersonEnrolments(... 'erased')` has ended active ones in the same transaction) | journey state has no legal retention need |
| `automation_runs` | `person_id`, `reason`, `data` | every run: time, automation, step, outcome, reason, email message id, task id | **deleted** under `SET LOCAL beam.allow_rewrite = 'on'`, before enrolments (FK order) | an append-only log, but it is marketing profile data; the erasure report keeps counts only |
| `automations`, `automation_versions`, `automation_groups` | none (staff user ids only) | not included | untouched | configuration, listed in `NO_PII_TABLES` |

- Order: ops's `ERASE_ORDER = ['webinar','automation','email',...,'crm','platform']` runs `automation` after `webinar` and before `email`. That is safe because `email_messages.enrolment_id` has no FK (email spec, section 2), so deleting enrolments first leaves only a dangling id that `email` then deletes or nulls; `automation_runs.email_message_id` is deleted with the runs. `erase` first calls `exitPersonEnrolments(..., 'erased')` so the count of ended journeys is in the report, then deletes runs and enrolments. Pending `automation.step` jobs for the erased person find no enrolment and finish as no-ops.
- Restriction and objection (ops rules 65 and 66) call `exitAllForPerson`; marketing enrolment is refused while `persons.processing_restricted_at` is set (A-11; ops' `processing_restrictions` table is not read); lifting a restriction re-enrols nobody (the person re-enters only through a new trigger with consent).
- Aggregate numbers on `/admin/automations` are computed from the tables, so erased people drop out of counts; this is accepted.
- `automation_enrolments.context` never holds sensitive data (A-7). Exports go to the subject only through `ops`'s `privacy.export`; staff exports of runs show ids and outcomes only.
- Retention (rows in `retention_policies`, seeded by `ops` and inserted `on conflict (key) do nothing`; enforced by `privacy.retention_sweep` calling this module's `sweep[key]` handlers, which call `purgeAutomationHistory(tx, key, cutoff)` exported from `privacy.ts`; keys per Convention 4 and cross-module D37): `automation.automation_runs`: `automation_runs` older than 730 days -> delete; `automation.automation_enrolments`: `automation_enrolments` with `ended_at` older than 1,095 days -> delete (runs first). `re_entry: never` is therefore "never within three years". Active enrolments are never purged.
- `privacy.test.ts`: after `erase`, no row in either table references the person; `export` returns every enrolment and run; `gdpr-coverage` finds both tables registered; `sweep` has exactly the keys `automation.automation_runs` and `automation.automation_enrolments`; a restricted person is not enrolled into a marketing journey but is enrolled into `waitlist-offer`.
- The webhook step sends only `WEBHOOK_ALLOWED_FIELDS`; a BEAM-configured webhook receiver is a recipient BEAM must list in its own records of processing; the allow-list editor shows that warning.

## 11. Edge cases and failure modes

| # | Case | Decided behaviour |
| --- | --- | --- |
| 1 | Two ticks overlap and both start `automation.evaluate` | The second fails to get `FOR UPDATE SKIP LOCKED` on the cursor row and returns at once; the job keys per minute also prevent duplicates. |
| 2 | A transaction commits event 105 before event 104 becomes visible | 104 is recorded as a gap and re-read on the next passes; it is processed when it appears, or dropped after 10 minutes (rolled back). |
| 3 | The same event is processed twice (gap re-read, retry) | `uq_enrolment_trigger` rejects the second enrolment (`on conflict do nothing`); exits find no active enrolment; run `dedupe_key` rejects duplicate log rows. |
| 4 | An event both exits and triggers for the same person (purchase ends lead nurture and starts nothing, attended ends `welcome-lead` and starts `after-first-visit`) | Exits run first (A-9), so the domain is free and the new journey enrols without `superseded`. |
| 5 | A person attends a webinar and the 15-, 30-minute and end events arrive in one batch | Processed in id order; each higher-priority journey supersedes the previous before its first step (anchor +60 min) is due; the timeline shows `entered` and `exited: superseded` for each. |
| 6 | Unsubscribe arrives while `automation.step` for that person is running | Both lock the enrolment row; whichever runs second sees the other's result. If the step already queued the email, `email.send` sees the suppression and marks the message `suppressed`. |
| 7 | A marketing step is due but the person withdrew `newsletter` consent without a suppression | The built-in `consent.withdrawn` exit ends marketing journeys with that purpose; any remaining marketing step in a transactional journey is `skipped_unreachable`. |
| 8 | The template lacks the person's locale (French template missing for an `fr-BE` person) | `skipped_translation`, the journey continues with the next step, the daily digest counts it; nothing is sent in another language. |
| 9 | A template referenced by an active automation is archived | Publish validation prevents new versions with it; at send time no published version exists -> `failed` with reason `template_unavailable` and an alert; the journey continues. |
| 10 | The anchor moves | Two cases. (a) The customer reschedules the booking to another session: `booking` writes `booking.rescheduled`, `booking.cancelled` for the old row (code `rescheduled`) and `booking.confirmed` for the new one (booking's catalogue, cross-module D53, section 10.1), so `event-registration` and `after-first-booking` exit on the old subject and enter on the new one with the new anchor. (b) Staff move the session itself: when the subject is `booking:<id>` and the anchor is `data.starts_at`, `automation.step` re-reads the session's current `starts_at` through `v_person_bookings` before a time-relative step; if it moved by more than 5 minutes it updates `anchor_at`, re-plans the pending steps (a `scheduled` row with reason `anchor_moved`; steps now in the past are `skipped_late_entry` with reason `anchor_moved`) and sends nothing in that run. |
| 11 | The automation is paused for 3 days, then resumed | During the pause no step runs and no one enrols; exits still apply. On resume, time-sensitive steps more than 24 h overdue are `skipped_paused`; later steps run on time. |
| 12 | The platform was down 30 hours (no ticks) | Email, Slack and webhook steps more than 24 h late are `skipped_stale`; tasks and tags still apply; the sweep alerts on the backlog. |
| 13 | Staff publish v2 while 400 people are in v1 without ticking migrate | v1 enrolments run to the end on v1; new entries use v2; the enrolments screen shows the version per row. |
| 14 | A migrated enrolment's v2 renamed a step key | The renamed step counts as new: if its due time is past it is `skipped_late_entry` (reason `migrated`), otherwise it runs. Keys are the identity of a step; the editor warns when a key changes on an automation with active enrolments. |
| 15 | A `task` step's role has no active staff user | The owner falls back to the active `management` user with the fewest open tasks, then to an `owner`; run `task_created` with reason `owner_fallback:<role>`. With no staff at all the step is `failed` (`no_staff_user`). |
| 16 | An `enrol` step points at an automation that is paused or archived | Entry refused: run on the source enrolment is `skipped_condition` with reason `target_inactive:<slug>`; journeys never chain into dead ones. |
| 17 | Two automations `enrol` each other | Allowed only through re-entry rules; `never` or `after_days` stop loops. Validation refuses an `enrol` step targeting an automation whose `re_entry` is `always` and which itself enrols back (direct cycle). |
| 18 | The person is merged while enrolled | The loser's active enrolments exit `merged`; the winner keeps its own; history stays on the loser id and `crm` shows merged persons' timelines on the winner. |
| 19 | The person is erased while a step job is queued | The erase deletes enrolments and runs; the job loads no enrolment and succeeds as a no-op; `email.send` refuses erased persons. |
| 20 | A staff member enrols someone into a marketing journey who is unsubscribed | Enrolment succeeds (staff override of entry rules) but every marketing step is `skipped_unreachable`; the dialog warns before confirming. Consent can never be bypassed. |
| 21 | A segment of 20,000 people is enrolled at once | `automation.enrol_segment` on the bulk lane, 500 per job; first steps spread over about 40 ticks; marketing sends stay subject to the R2 frequency cap and the email warm-up limits owned by `email`. |
| 22 | A definition with an invalid `where` path is published | Paths are validated against a typed list of known event data paths when the kind is in the event registry; unknown kinds or paths produce a warning (not an error) so new events from other modules work; at run time a missing path simply does not match. |
| 23 | A person with an existing future booking reaches 30 days inactivity | `d30` is `skipped_condition` with reason `unless:has_future_booking`. |
| 24 | A grant hits 90 % and the customer buys a new package the same day | `credits.granted` with `source = purchase` and the same `credit_kind` exits `package-usage` (a package of another kind does not); if the 90 % email was not yet sent it never goes; if it was, nothing follows. |
| 25 | `booking.attended` is later corrected to `no_show` by staff before the review request is sent | `booking.no_show` with the same subject exits the enrolment; the send-time `booking_status_in` check catches it even if the exit event is late. |
| 26 | The go-live import loads 12,000 persons, bookings, packages and consents | Imported facts carry `data.source = 'import'` (or go to ops's `imported_history`) and are older than 48 hours, so nothing enrols (A-7); suppressions imported first keep every unsubscribed person unreachable for later journeys ("suppression survives an import"). |
| 27 | A tag step applies `engaged`, crm writes `tag.added` | The event carries `data.source = 'automation'` and never triggers (A-7c); it still feeds segments and the B2C stage. |
| 28 | A customer asks for restriction of processing while in `welcome-lead` and `waitlist-offer` | ops calls `exitAllForPerson(..., 'restricted')`: `welcome-lead` exits `restricted`, `waitlist-offer` (transactional) keeps running; new marketing triggers write `skipped_unreachable` reason `restricted` until the restriction is lifted. |
| 29 | Staff pause an automation between the evaluator's enqueue and the step job's run | The job finds the automation paused and succeeds without effect; on resume `automation.resume_enrolments` enqueues the step with the `:resume:` key (A-26a), because the original key is still taken by the succeeded job row. |
| 30 | One consume crosses 75 % and 80 % of the same grant | credits writes two events in id order; the 80 % event's `exit_on` ends the 75 % enrolment (A-22 guard keeps the 80 % one) and the 80 % journey enrols; the 75 % email goes only if its step already ran. |
| 31 | A task step falls due on Easter Monday | `booking.nextOpeningAt` moves the due time to Tuesday's opening time; the run reason records `due_moved:<iso>`. |
| 32 | The evaluator falls behind (a campaign floods `email.opened` events) | Continuation jobs process 1,000 events per run; when the oldest unprocessed event is older than 5 minutes the sweep alerts `automation-lag` (A-45); suppression exits do not depend on the evaluator (A-23). |
| 33 | A step job dies after 6 attempts (template renderer bug) | Platform alerts the dead job and calls its `onDead` hook, which writes `failed` with the error and advances the enrolment at once, so later steps still run; if the hook throws, the sweep does the same within 15 minutes (A-35). |
| 34 | ops withdraws the `watch_time_profiling` DPIA approval while webinar behaviour journeys are active | The next evaluator run pauses every active automation with `requires_dpia = watch_time_profiling` (the eight of A-5a, including `webinar-cta-sales-task`) (audit actor `system`, Slack `automation-dpia:watch_time_profiling`); Resume and Activate return `conflict` until the decision is approved again. `webinar-registration`, `webinar-no-show` and `webinar-poll-answer` keep running. |
| 35 | A staff member saves a draft triggered by `ops.history_imported` | Saved with issue `trigger_history_imported`; Publish is refused (A-1); imported history never starts a journey. |
| 36 | `ff_commerce_checkout_recovery` is switched off while people are in `abandoned-checkout` | New `checkout.abandoned` events enrol nobody; due steps write `skipped_condition` reason `flag_off:ff_commerce_checkout_recovery` and the enrolments complete; switching the flag on later affects only new abandonments (A-11a). |

## 13. Decisions made

Additions to the architecture (tables, columns, enum values, settings keys):

1. `automation_groups.lane` (text, null): groups sharing a lane form one exclusivity domain. Seeded lane `sales_journey` joins `customer_journey` (10), `webinar` (20), `waitlist` (25) and `lead_nurture` (30), so lead, customer, waitlist and webinar sales journeys never run at the same time (blueprint 21), while the architecture's per-group rule still holds when `lane` is null.
2. Extra seeded groups `review`, `sales`, `checkout` (non-exclusive), so review requests, task-only journeys and checkout recovery neither block nor supersede sales journeys.
3. `automations.priority`, `draft_definition`, `draft_updated_at`, `draft_updated_by_user_id`, `activated_at`, `paused_at`, `last_resumed_at`. Drafts live on the automation, so every `automation_versions` row is a published, immutable version.
4. `automation_versions.definition_hash` and `change_note`.
5. `automation_enrolments.subject_key`, `group_id`, `exclusive_domain`, `source`, `trigger_event_id`, `plan`, `entered_by_user_id`, `migrated_from_enrolment_id`. The architecture's partial unique `(automation_id, person_id) where active` is widened to `(automation_id, person_id, subject_key)`; with `subject_key = ''` it is the same rule. Without it a person registered for two events would get only one confirmation.
6. Two more partial unique indexes: one active enrolment per person per exclusive domain, and one enrolment per `(automation_id, trigger_event_id)` (idempotent re-reading).
7. `automation_runs.automation_version_id`, `data`, `actor`, `dedupe_key`; `enrolment_id` nullable for entry decisions that create no enrolment.
8. Outcome values added: `tag_removed`, `status_set`, `enrolled`, `notified`, `webhook_called` (one per step type that the architecture's list lacked), `skipped_stale` (overdue after an outage, not a pause), `skipped_frequency_cap` (R2).
9. `settings` key `automation_rules` = `{ max_marketing_per_day: 1, max_marketing_per_week: 3, quiet_start: '21:00', quiet_end: '08:00', webhook_hosts: [] }`; `settings.automation_cursor` = `{ last_event_id, gaps: [{ id, first_seen_at }] }`.
10. Views `v_automation_stats`, `v_automation_due`, `v_person_automation_timeline`.
11. New environment variable `AUTOMATION_WEBHOOK_SECRET` and a new integrations client `packages/integrations/src/webhook/` with `fake.ts`.

Engine choices:

12. Gap-safe cursor: missing identity ids are remembered and re-read for 10 minutes, because identity values commit out of order; idempotent enrolment makes re-reading safe.
13. Fixed per-event order: built-in exits, `exit_on` exits, then triggers by priority. Built-in exits (erased, merged, suppression, consent withdrawal) apply even when a definition forgets them.
14. Late-entry skip applies only to steps timed from the enrolment or the anchor; steps timed from the previous step are never late. `late_entry: send_now` exists for steps that must still go (first-visit preparation).
15. `event-registration` reminders are 7 days, 3 days and 3 hours before the start (no 1-day reminder), so a Friday registrant for a Sunday event receives exactly the confirmation (booking's `booking.booking_confirmed`) and the day-of reminder, as the proposal states for scenario 1. In V1 scenario 1 runs on event sessions (`booking.confirmed` of kind `event`), because the native webinar is Release 2 and V1 webinar imports never enrol (A-7); in R2 this module's seeded `webinar-registration` journey (`d7`, `d3`, `h3`) shows the same skip.
16. Overdue rule: communication steps more than 24 hours late are skipped (`skipped_paused` or `skipped_stale`); tasks, tags and field changes still apply.
17. A paused automation still processes exits, so an unsubscribe ends a paused journey too.
18. Conditions are evaluated on fresh facts at step time; nothing is cached at entry except the trigger context.
19. Templates are resolved at send time to their current published version, so marketing fixes a typo without republishing the journey; `email_messages.template_version_id` keeps history exact.
20. Reachability is per step by the template's kind and purpose; an automation's `is_marketing` and `purpose` decide the entry check and which suppressions and consent withdrawals end it.
21. Failed audience and re-entry checks are not logged (noise); `skipped_exclusive`, `skipped_unreachable` at entry and `failed` (anchor missing) are logged with `enrolment_id` null.
22. Staff enrol and move override re-entry, audience and exclusivity (a blocking journey exits `moved`) but never consent or suppression.
23. Task owner: active staff user of the role (from `platform.listStaffForAssignment(tx, { roleKey })`, platform's only name for it) with the fewest open tasks, then `management`, then `owner`; with `owner: trigger_owner`, the trigger's `owner_user_id` when active. Due dates roll to the next opening time (decision 47).
24. Webhook payloads carry only `WEBHOOK_ALLOWED_FIELDS`, signed with HMAC SHA-256, https only, hosts on an allow-list editable with `settings.write`.
25. Slack texts may only use `{{first_name}}`, `{{person_url}}`, `{{automation}}`; no email, phone or sensitive data leaves through Slack.
26. The module emits no `activity_events`; the timeline reads `automation_runs`, and the evaluator ignores `automation.*` kinds, which rules out feedback loops.
27. Names, task titles and Slack texts are plain staff-facing text, not `LocalizedText`; every customer-facing word is in an email template.
28. Read access to automation screens uses `reports.read` or `automations.write`; pause, resume, activate, archive and segment enrolment need `automations.publish`; the rules page needs `automations.publish` and the webhook host list also `settings.write`. No new permission strings.

Release and content choices:

29. Group exclusivity and priority are enforced by the engine in V1 (needed so V1 journeys do not contradict each other); the proposal's Release 2 item "automation conflict rules" ships as the editable groups, frequency caps, quiet hours and the conflict report.
30. R2 journeys (this module's webinar behaviour set, `abandoned-checkout`, `waitlist-follow-up`, `event-follow-up`) are seeded in V1 as `draft` with a published version and switched on by `activateReleaseSequences` in automation-P8; a journey BEAM deactivated is never re-activated by a seed.
31. The waitlist claim email with the single-use token is sent by `booking`, which alone holds the raw token; the automation sends the 30-minute expiry reminder linking to the portal waitlist page.
32. `review-request` is a marketing journey with purpose `newsletter` (conservative reading of ePrivacy); BEAM can change the purpose in the editor. The trigger is `booking.attended` only, re-entry `after_days:30`, and the booking status is re-checked at send time.
33. Package usage covers 50, 75, 80, 90 % and the last unit (blueprint 21 and 31 combined): emails at 50, 75, 90 and last, a tag at 80; every step stops on repurchase (`credits.granted` with `source = purchase` and the same `credit_kind` as exit, credits section 4, plus `has_other_active_grant`).
34. B2C pipeline: the stage stays computed by `ops`; automations drive changes by producing the facts (tag `engaged`, bookings, orders) and react to `ops.stage_changed` with one playbook journey per stage (task, owner, deadline, escalation).
35. B2B journeys in R3 create tasks and Slack messages only; automated B2B outbound email is "Later".
36. The R4 builder is a vertical flow editor built without a graph library, so no dependency request is needed.
37. Retention: `automation.automation_runs` 730 days, `automation.automation_enrolments` (ended enrolments) 1,095 days (aligned with ops' 3-year `ops.marketing_profile` rule), run by this module's `sweep[key]` handlers; `re_entry: never` means never within that window.
38. Seed copy for every template is placeholder text in nl-BE, fr-BE and en, replaced by BEAM before go-live; seeds never overwrite edited rows.
39. Requirements placed on other modules (recorded in their PRs): `crm` puts `acquisition_source` in `person.created` data, writes `data.source = 'automation'` on events caused by automation steps, exposes `findPersonIdsByEmailHash` and `updatePersonFields` (both exist in crm 4.8), calls `isSegmentInUse` in `archiveSegment` and renders `PersonAutomationsPanel`; `booking` writes, on a reschedule, `booking.rescheduled`, `booking.cancelled` for the old row and `booking.confirmed` for the new row, defaults `reminder_hours_before.event` to `[]`, and has `nextOpeningAt` in its api (all settled by cross-module D53 and D16); `credits` carries `credit_kind` in every credits event (cross-module D27); `commerce` already provides `total_cents` in `checkout.abandoned`, `getCheckoutRecoveryProps` and `markCheckoutRecoveryMessage`; `email` provides `queueMarketingEmail`, `queueAutomationEmail`, `getPublishedTemplateInfo`, `getTemplateInfo`, `listPublishedTemplates`, `seedTemplate` with its own signatures (adopted here) and calls `isTemplateInUse`; `webinar` seeds only its marketing template `webinar-follow-up` (this module seeds every webinar journey; email's seed creates the system rows of `webinar.reminder` and `webinar.replay_available`); `ops` seeds the two retention rows `automation.automation_runs` and `automation.automation_enrolments`, calls `exitAllForPerson` and provides `isDpiaApproved`; `platform` provides `onDead`, `listStaffForAssignment`, `notifySlack` and `flag`. Every event name in this spec is the owner's name (booking 4.7, credits section 4, commerce, forms, ops, webinar 4.1).
40. `automation_versions` and `automation_runs` are append-only through Wave 0's `APPEND_ONLY_TABLES`, which already lists both; the orchestrator's custom migration `select beam_protect_append_only();` after each wave attaches the trigger once the tables exist. The earlier request to add them is withdrawn (cross-module D43).
41. Imported, stale (older than 48 hours) and automation-caused events never trigger (A-7), so the go-live data migration, a backfill or a tag step cannot send old or looping messages.
42. Events whose kind the owner does not emit are not used. `person.erased` does not exist (erasure deletes the timeline), so erasure ends journeys through `exitPersonEnrolments` in automation's own `privacy.erase`.
43. Booking owns the booking confirmation and the day and night reminders; automation owns event reminders (`event-registration`, scenario 1 in the automation log), first-visit preparation and the intake reminder. No email is sent by both.
44. New seeded journeys closing blueprint 22 and 31: `assessment-follow-up` (assessments; marketing, so a result without newsletter consent receives only forms' transactional result email), `package-expiry` (packages and gift vouchers, transactional notice 30 and 7 days before expiry), `package-finished` (finished but not repurchased), `member-welcome` (members), the `d180` dormant step, and R2 `event-follow-up` and webinar behaviour journeys.
45. Health alerts (A-45) run every 15 minutes from the sweep. Dead step and webhook jobs are recorded by platform's `onDead(ctx, input, error)` hook (PL-29a) through `recordDeadStep`; the sweep only covers a hook that threw (A-35).
46. Evaluator runs are single transactions (the job contract) of at most 1,000 events with one savepoint per event and a continuation job; no evaluator transaction holds person locks for more than about 30 seconds.
47. Task due dates move forward to the next opening time of the centre (`booking.nextOpeningAt`, which includes Belgian public holidays and closed days), so tasks never fall due when nobody is in.
48. Frequency caps and quiet hours (R2) are edited with `automations.publish` by marketing; adding a webhook host also needs `settings.write`.
