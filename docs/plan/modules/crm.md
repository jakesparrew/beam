# Module `crm`: Customer core

Owner of identity, consent, suppressions, the timeline, tags, segments, tasks, companies, the B2B pipeline and the unified inbox. Blueprint sections 3, 4, 5, 6, 24, 25, 29, 35, 36, 37, 54, 59, 60 are primary; requirements from 16, 17, 19, 20, 21, 30, 36, 44, 53, 55, 56, 62, 63 and 76 also land here, plus wellness-centre needs the blueprint left out (emergency contact, house rules and health declaration, minors, reception quick view, accessibility). This spec follows `docs/plan/00-decisions.md` and `docs/plan/01-architecture.md`. Every addition to the architecture is listed in section 13.

## 1. Purpose and release mapping

`crm` is the one place a person exists. Every other module refers to `persons.id`, writes facts to `activity_events`, and asks this module whether a person may be contacted. Staff see the whole relationship with a customer on one screen (`/admin/persons/[id]`).

| Release | Weeks | What `crm` ships |
| --- | --- | --- |
| **V1** | 1–6 | `persons` with derived status and a manual override; acquisition origin captured once; locale; customer number and legacy external ids; search; duplicate detection (email variants, phone, name, legacy id) with a review queue; staff merge that keeps all history (`person_merges`); encrypted sensitive fields read only through `readSensitive()`; consent per purpose with wording version, source, method, lawful basis and withdrawal; `v_consent_current`; suppressions separate from contacts and immune to imports; one-click unsubscribe and the token-based preference centre; the `activity_events` catalogue and the customer 360 page; manual notes and logged interactions (sensitive notes encrypted); tags; dynamic and static segments with exclusions, the segment compiler and `SEGMENT_ALLOWED_FIELDS`, hourly refresh; tasks with owner, due date, priority, related person or company and overdue visibility; companies and company contacts with decision roles (one person can be both B2C customer and B2B contact); portal pages for personal details and communication preferences; privacy registration of every crm table. Wellness-centre additions the blueprint left out: an emergency contact per person (nights), versioned guardian consent for minors (`person_declarations`, kind `guardian_consent`) that reception records, a reception quick view in the 360 header that also shows site's terms acceptance (house rules and health self-declaration) and forms' `health-declaration` form state (cross-module D15), and the Belgian age-of-consent rule for marketing (13 years). |

## 2. Domain model

All tables live in `packages/db/src/schema/crm.ts`; views in `packages/db/src/schema/crm.views.ts`. Conventions from architecture section 2 apply (uuid `id` with `gen_random_uuid()`, `created_at timestamptz not null default now()`, `updated_at` on mutable tables, enums named `<table>_<column>`). Wave 0 already created `persons`, `activity_events`, `consent_records` and `suppressions` with their architecture columns; this module adds columns to them in its own file (expand only) and creates the rest. `audit_log` is platform's table in `platform.ts` (architecture section 2 and platform spec decision 13), even though the Wave 0 list in architecture section 11 names it with crm; crm writes it only through `ctx.audit()` and never declares it. Wave 0 also creates `apps/web/modules/crm/*.ts` stubs and empty `crm.json` catalogues; crm-P1 replaces their content, it does not create them. **APPEND** = insert-only via the `reject_update_delete()` trigger (registered in `APPEND_ONLY_TABLES`). **SENSITIVE** = declared with `sensitive()` and listed in `SENSITIVE_COLUMNS`. Shared types in `packages/core/src/crm/types.ts`: `Locale = 'nl-BE'|'fr-BE'|'en'`, `LocalizedText`, `PostalAddress = { street?: string; number?: string; box?: string; postal_code?: string; city?: string; country: string /* ISO 3166-1 alpha-2, default 'BE' */ }`, `Actor` (architecture section 3).

### 2.9 Views (`crm.views.ts`)

```sql
-- latest record per person and purpose
create view v_consent_current as
select distinct on (person_id, purpose) person_id, purpose, status, lawful_basis, method, source,
       wording_version, recorded_at,
       case when status = 'granted' then recorded_at end as granted_at,
       case when status = 'withdrawn' then recorded_at end as withdrawn_at
from consent_records order by person_id, purpose, recorded_at desc, created_at desc, id desc;

-- one row per person and marketing purpose
create view v_suppression_status as
select p.id as person_id, pr.purpose,
  (exists (select 1 from suppressions s where s.email_hash = p.email_hash and (
      s.scope = 'all'
      or (s.scope::text = pr.purpose and not (s.reason = 'unsubscribe' and exists (
            select 1 from v_consent_current c where c.person_id = p.id and c.purpose::text = pr.purpose
              and c.status = 'granted' and c.method in ('form','portal','preference_centre')
              and c.recorded_at > s.created_at)))))
    or p.erased_at is not null or p.email is null or p.processing_restricted_at is not null) as is_suppressed
from persons p cross join (values ('newsletter'),('events'),('member_comms'),('b2b')) pr(purpose)
where p.merged_into_person_id is null;

-- manual status that no longer matches the calculated status
create view v_status_override_conflicts as
select p.id as person_id, p.status_override, s.derived_status, p.status_override_at, p.status_override_by_user_id
from persons p join v_person_status s on s.person_id = p.id
where p.status_override is not null and p.status_override::text <> s.derived_status::text
  and p.erased_at is null and p.merged_into_person_id is null;

-- latest declaration per person and kind, with validity
create view v_declaration_current as
select distinct on (person_id, kind) person_id, kind, status, document_version_id, accepted_at, expires_at,
       (status = 'accepted' and (expires_at is null or expires_at > now())) as is_valid
from person_declarations order by person_id, kind, accepted_at desc, id desc;

create view v_open_tasks as
select t.*, (t.due_at < now()) as is_overdue,
       (t.due_at >= date_trunc('day', now() at time zone 'Europe/Brussels') at time zone 'Europe/Brussels'
        and t.due_at < (date_trunc('day', now() at time zone 'Europe/Brussels') + interval '1 day') at time zone 'Europe/Brussels') as is_due_today
from tasks t where t.status = 'open';
```

R3 adds `v_opportunity_board`: every opportunity joined with `companies.name`, the owner's name, `last_contact_at = max(activity_events.occurred_at)` over events with that `company_id` or the primary contact's `person_id` and `kind in ('interaction.logged','email.sent','inbox.message_received','inbox.reply_sent','opportunity.stage_changed')`, `stage_deadline_at = stage_entered_at + playbook_stages.deadline_days`, and `is_stalled = now() > stage_deadline_at`.

## 3. Business rules

Numbered `3.n`. Each one has at least one test named after it (`it('3.7 ...')`).

**Identity**
1. One person per active email address: `lower(email)` is unique among persons that are neither merged nor erased. Emails are trimmed and lower-cased before storage; an empty string is stored as null.
2. `findOrCreatePersonByEmail` takes `pg_advisory_xact_lock(hashtext(lower(email)))`, then returns the active person with that address; if none, it follows a merged person with that address to its winner; only then does it create. Two concurrent calls for one address create exactly one person.
3. On an existing person, `findOrCreatePersonByEmail` and imports only fill empty fields (`first_name`, `last_name`, `phone`, `address`, `birth_on`). They never overwrite a non-empty value, never change `locale`, never change `acquisition`, and never touch consent or suppressions.
4. `acquisition` is written once, in the creating transaction. (R3) When the input carries `acquisition.referral_code` (the request handlers that create persons, namely forms' submit route, commerce's checkout, platform's customer sign-up and webinar's registration route, read it from site's `beam_ref` cookie with `site.readReferralCode()` and pass it as `acquisition.referral_code`, so persons created by forms carry it too; crm's api functions have no request of their own), the creating call resolves it with credits' `resolveReferralCode(tx, code)`: a known code stores the upper-cased `referral_code` and fills `referrer_person_id` and `partner_company_id` when the caller left them empty (a partner code also sets `persons.partner_company_id`); an unknown or inactive code is dropped without error. Before R3 the field is ignored. Later writes are refused with `conflict`, except staff with `persons.write` may fill it when the stored `source` is missing; that fill is audited. The acquisition source never feeds status, queue position or event priority.
5. `locale` is set on creation from the explicit form or portal choice, else the URL locale, else `Accept-Language`, else `nl-BE`. Only the person (portal, preference centre) or staff change it afterwards; each change writes `person.locale_changed`.
6. `customer_number` is assigned by the database and never reused. Staff search accepts `C-000123`, `123`, an email, a phone number (any format, normalised) or a name prefix.
7. `phone_e164` is derived from `phone` on every write with default country `BE` (`0470 12 34 56` → `+32470123456`, `0032...` → `+32...`). An unparseable phone keeps `phone` and leaves `phone_e164` null.

**Commercial status**
8. Derived status is `member` with an `active` or `past_due` membership that has started; else `customer` with at least one paid order (total above €0, status `paid`, `partially_refunded` or `refunded`) that contains a line of product kind `session`, `night`, `package`, `membership` or `ticket`, or a credit grant of source `purchase` or `import` with credit kind `day` or `night`; else `lead` (cross-module D28) (blueprint 3 and 19: "paid for at least one session, package, night or membership"). An order of only `item` or `voucher` lines (merchandise, a gift voucher bought for someone else) and a free event never make a customer. It comes from credits' `v_person_status`; crm never stores it. crm's tests pin this definition with a fixture view; credits must apply the product-kind filter to its `paid` CTE (see section 13, decision 9).
9. `status = coalesce(status_override, derived_status)`. Only `setStatusOverride` writes `status_override`; it locks the person row `FOR UPDATE`, requires a reason of 3–500 characters, writes `audit_log` action `person.status_override` with old and new value, and an activity event `person.status_overridden`.
10. A purchase, a membership or any job never clears or changes an override. An automation step `status_override` calls `setStatusOverride` only when no override exists; otherwise it logs `skipped_condition`.
11. When an override differs from the derived status, the person appears in `v_status_override_conflicts`; the 360 page shows a banner "Manual status *lead* differs from calculated *customer*" with buttons "Keep" (records `person.status_override_confirmed`, hides the banner until the derived status changes again) and "Clear override".
12. Member pricing and member-only booking use `is_member` from `v_person_status` (exposed as `hasActiveMembership` by `getPersonStatus`), never the override. Segments, lead-priority windows and status content blocks use `status`.

**Consent and suppression**
13. Consent is per purpose. `recordConsent` appends a row; nothing updates or deletes one outside erasure. `v_consent_current` is the latest row per `(person_id, purpose)` by `recorded_at`, then `created_at`, then `id`.
14. A grant with method `portal` or `preference_centre` requires a published `consent_wordings` version for that purpose and stores `<purpose>@<version>`. A grant with method `form` stores either `<purpose>@<version>` (webinar registration, site checkboxes) or `form:<slug>:v<version>:<field_key>`, whose wording is frozen in the published form version; any other string is a `validation` error. Imports may store `legacy-import`. Staff grants are allowed only for `b2b` with `lawful_basis = legitimate_interest`.
15. Delivering an assessment result never creates `newsletter` consent: only an explicitly ticked consent field of a form produces a grant, and only for the purpose that field declares.
16. Withdrawing a marketing purpose (`newsletter|events|member_comms|b2b`) appends `withdrawn`, inserts a suppression with that scope and reason `unsubscribe` through `addSuppression` (the only writer of `suppressions`; `on conflict do nothing`), which calls automation's `requestSuppressionExit(tx, { suppressionId })` in the same transaction (automation enqueues `automation.exit_for_suppression` with key `supp:<suppression_id>`, lane `fast`, priority 1; crm never enqueues the job itself), and records `consent.withdrawn` and `suppression.added`, all in one transaction. The action's `after()` kick runs the exit job, so running marketing sequences end within seconds (scenario 2).
17. "Unsubscribe from everything" writes `withdrawn` for every currently granted marketing purpose and a suppression with scope `all`.
18. Hard bounces and complaints (from the email module) insert scope `all` with reason `hard_bounce` or `complaint`; a complaint also withdraws every marketing purpose with method `complaint`. Both happen inside `addSuppression` (reason `complaint` appends `withdrawn` for every currently granted marketing purpose of every active person with that `email_hash`, records `consent.withdrawn`, in the same transaction), so email only calls `addSuppression` and never writes `consent_records`.
19. A suppression is never deleted. A scope-specific `unsubscribe` suppression stops blocking only when the person later gives a fresh grant for that purpose through `form` (after the confirmation email of rule 3.21), `portal` or `preference_centre` that is newer than the suppression. Scope `all`, `hard_bounce`, `complaint`, `manual` and `erased` block forever for that address.
20. Imports never write suppressions except an import of kind `suppressions`, and an imported consent grant is skipped (reported as `skipped: suppressed_or_withdrawn`) when the address is suppressed for that scope or `all`, or the person has any `withdrawn` record for that purpose. "Suppression survives an import" is an acceptance test.
21. A form grant for a purpose blocked by an `unsubscribe` suppression is not recorded directly: crm sends `crm.confirm_resubscribe` with a preference-centre link, and the grant is recorded with method `preference_centre` when the person confirms.
22. Persons with `processing_restricted_at` set, no email, or `erased_at` set are suppressed for every marketing purpose in `v_suppression_status` and excluded from every segment.

**Sensitive data**
23. Sensitive values exist only in `person_sensitive_fields.value_enc`, in `activity_events` rows with `is_sensitive = true`, and (forms module) `form_sensitive_answers`. Plain values never appear in `data`, logs, Sentry, segments, exports for staff, or AI context.
24. Reading a sensitive value goes only through platform's `readSensitive(ctx: Ctx, personId: string, purpose: 'staff_view' | 'privacy_export' | 'subject_result', scope?: { keys?: SensitiveFieldKey[]; eventIds?: string[]; submissionIds?: string[] }): Promise<SensitiveBundle>` (in `apps/web/lib/sensitive.ts`, imported through `apps/web/modules/platform/api.ts`; cross-module D11). `staff_view` needs a staff actor with `persons.sensitive_read`; `privacy_export` needs the system actor; `subject_result` needs the system actor and a non-empty `submissionIds` of the person's own submissions. It writes `audit_log` action `sensitive.read` with the purpose and the keys or event ids read, never the values. crm uses `staff_view` for staff reveals and `privacy_export` for the export handler. The returned `SensitiveBundle = { fields: Partial<Record<SensitiveFieldKey, string>>; formAnswers: { submissionId; fieldKey; value }[]; notes: { eventId; body }[] }` carries the person's sensitive notes (`is_sensitive` activity events) decrypted, so crm never calls `decryptSensitive` itself (section 13 decision 41). The purposes `care` and `customer_request` and a bundle field `events` do not exist.
25. Writing a sensitive field needs `persons.sensitive_read`, writes `audit_log` action `sensitive.write` with `old_value`/`new_value` = `{ key, changed: true }` only, and an activity event `sensitive.updated` with `data = { key }`.
26. A staff note marked sensitive is stored as an `is_sensitive` event; the timeline shows "Sensitive note" with a Reveal button for holders of `persons.sensitive_read`; revealing calls `readSensitive(ctx, personId, 'staff_view', { eventIds: [eventId] })` and shows only the requested note.
27. `SEGMENT_ALLOWED_FIELDS` and `SEGMENT_ALLOWED_EVENT_KINDS` contain no `SENSITIVE_COLUMNS` member and no `is_sensitive` events (unit test).

**Duplicates and merge**
28. Duplicate candidates are scored by fixed rules: same legacy external id 95; same email after removing dots and `+tag` for gmail.com and googlemail.com addresses 90; same `phone_e164` 80; same lower-cased first and last name and same `birth_on` 70; same name and same postal code 50. Scores of several reasons do not add up; the highest counts. Pairs scoring 50 or more are stored as `open` candidates; a `dismissed` pair is never re-proposed.
29. Creating a person in the admin shows candidates scoring 50 or more before saving; staff confirm "create anyway". Every create and every change of email, phone, name or birth date enqueues `crm.check_duplicates`.
30. A merge needs `persons.merge`, two distinct persons that are neither erased nor merged, and an explicit winner. The merge runs in one transaction: lock both rows `FOR UPDATE` (lower id first); apply the field choices to the winner; call the owner merge hooks in this order, each inside the same transaction: webinar's `mergePersons(tx, winnerId, loserId)` (R2; collapses double registrations) and credits' `onPersonsMerged(tx, ctx, { winnerPersonId, loserPersonId })` (grants, memberships, package shares, R3 referral rows); then repoint every foreign key column referencing `persons.id` in non-append tables from loser to winner; copy consent; set `merged_into_person_id = winner` on the loser and on every person already merged into the loser (chains stay one level deep); insert `person_merges`; set every `person_duplicate_candidates` row of the pair to `merged`; call platform's `reassignCustomerAccount(ctx, { fromPersonId: loser, toPersonId: winner })` so a portal login of the loser lands on the winner; call automation's `exitPersonEnrolments(tx, { personId: loser, reason: 'merged', actor })`; write `audit_log` action `person.merge` and the event `person.merged` on both persons.
31. Merge refuses with `conflict`, listing the cause, when both persons hold an active or past-due membership, or both hold an active booking for the same session, or both are on the same waitlist. For tables with a unique key that includes the person (`person_tags`, `segment_members`, `company_contacts`, `person_sensitive_fields`, `campaign_recipients`), the winner's row is kept and the loser's row is deleted after being described in `repointed`. Tables an owner hook handles are `skip` in `MERGE_STRATEGIES` and never touched by the generic repoint or delete: `webinar_registrations` (a generic delete would cascade into append-only `watch_segments` and `webinar_interactions`), `credit_grants.person_id`, `memberships.person_id`, `package_shares.shared_with_person_id`, and R3 `referral_codes.person_id` and `referral_attributions.*`. The hook results are stored in `person_merges.repointed` under `hook:webinar` and `hook:credits`. `users.person_id` is `skip` (platform's `reassignCustomerAccount` handles it); ops' `person_stats` loser row is deleted and `ops.requestStatsRefresh(tx, winner)` is called; ops' `processing_restrictions` keeps the winner's row, else moves the loser's; a restriction on either person carries over (`processing_restricted_at = least(both)`), so a merge never lifts a restriction.
32. Append-only tables (`activity_events`, `consent_records`, `person_declarations`, `credit_entries`, `automation_runs`, `audit_log`, `watch_segments`, `webinar_interactions`, `email_events`) are not rewritten. Reads resolve the merge: `resolvePersonIds(winnerId)` returns the winner plus every person whose `merged_into_person_id` is the winner (one level, because merges flatten), and the timeline, export and erasure use that list.
33. Consent on merge: for each purpose, the latest record across both persons wins; if it belongs to the loser, a copy is appended to the winner with the original `recorded_at`, `wording_version`, `method` and `source`, and `copied_from_record_id`. A withdrawal on either side newer than the other's grant therefore survives.
34. Merge keeps the oldest `acquisition` of the two (by `persons.created_at`), the winner's override (else the loser's), `is_tester` if either is a tester, and the union of `external_ids` (winner's value wins on a key clash).

**Timeline**
35. Every module writes timeline facts only through `recordEvent()` with a kind declared in a module's `events.ts`; an undeclared kind throws. `dedupe_key` makes a repeated fact a no-op.
36. Registered, started, attended and watched are distinct kinds (`webinar.registered`, `webinar.started`, `webinar.attended`, `webinar.watched`), and live, replay and on-demand activity carry `mode`; the timeline labels and filters on both.
37. The 360 timeline lists events of `resolvePersonIds(id)` newest first by `(occurred_at, id)`, 50 per page, with category filters; it renders every catalogue kind through its registered summary, and an unknown kind as its raw kind string.

**Segments**
38. The compiler accepts only fields in `SEGMENT_ALLOWED_FIELDS` with the operators allowed for their type, event rules only for kinds in `SEGMENT_ALLOWED_EVENT_KINDS`, at most 50 rules and depth 4; anything else is a `validation` error naming the rule path. Values are always bound parameters.
39. A dynamic segment's members are the rule result minus erased, merged and restricted persons. A static segment's members are its manual list minus the same. Members of every segment in `exclude_segment_ids` are removed at read time (`segmentAudienceSql`). A segment rule `in_segment` may reference other segments; cycles are refused on save.
40. `segments.refresh` runs hourly at minute 7 and refreshes each non-archived dynamic segment; saving a segment and planning a campaign refresh it on demand. A refresh first takes `pg_advisory_xact_lock(hashtext('segment:' || segment_id))`, so a scheduled, a manual and a campaign refresh of one segment run one after the other. A refresh writes `segment.entered` and `segment.left` events (dedupe `segment:<id>:<enter|leave>:<person_id>:<computed_at as YYYYMMDDHH>`), and updates `last_count` (after exclusions) and `last_counted_at`.
41. A failing refresh stores `refresh_error`, keeps the previous members, and shows the error on the segment page; the next refresh retries.

**Tasks**
42. A task needs an owner. Without `tasks.all` a user sees and edits only tasks they own and creates tasks only for themselves. Completing sets `done_at` and `done_by_user_id` and records `task.completed` on the related person or company. Task states: `open → done` (`completeTask`), `open → cancelled` (`cancelTask`), `done → open` and `cancelled → open` (`reopenTask`, clears `done_at` and `done_by_user_id`, records `task.reopened`). Any other transition is `conflict`. Each transition locks the task row `FOR UPDATE`.
43. A task is overdue when `status = 'open'` and `due_at < now()`. Overdue tasks are red in every list, counted in the admin navigation badge for the owner, and listed first in "My tasks".
44. A task with a `dedupe_key` is created at most once; automation passes `automation:<enrolment_id>:<step_key>`, retention passes `retention:<reason>:<person_id>:<ISO week>`.

**Companies and pipeline**
45. A company VAT number is normalised (spaces, dots removed, upper case) and unique. Linking a person to a company never changes their B2C status, consent or bookings.
46. (R3) Changing an opportunity's stage sets `stage_entered_at`, records `opportunity.stage_changed`, applies the stage's `default_probability_pct` unless staff changed the probability by hand on this stage, and creates one task for the opportunity owner titled from `required_action` due `deadline_days` later (dedupe `playbook:<opportunity_id>:<stage>:<stage_entered_at epoch>`); if the stage has an `automation_slug`, the primary contact is enrolled through automation's `enrolPersonBySlug(tx, { slug: automation_slug, personId })`.
47. (R3) `won` sets `won_at` and probability 100; `lost` requires `lost_reason` and sets probability 0. Won and lost opportunities leave the open board columns. Stage transitions: any open stage (`target` … `negotiation`) may move to any other open stage, `won` or `lost`; `won → account_management → renewal`, and `renewal → won` (renewed) or `lost`; `lost → target` reopens (clears `lost_at` and `lost_reason`, records `opportunity.reopened`); `won → lost` and moves back from `account_management` or `renewal` to an open stage are `conflict`. `moveOpportunityStage` locks the row `FOR UPDATE` and checks `version`.
48. (R3) An opportunity stalled beyond `escalation.after_days` in one stage creates one task for the first user with role `escalation.notify_role` and one Slack line (dedupe `escalate:<opportunity_id>:<stage>:<stage_entered_at epoch>`).

**Inbox**
49. (R3) An inbound message is linked to the active person whose email (or stored Meta sender id in `external_ids.meta_psid`) matches; otherwise the thread has no person until staff link or create one. Inbound messages never create persons or consent automatically.
50. (R3) A new inbound message on a `resolved` thread reopens it. A staff reply sets `first_response_at` once and moves `open` to `pending`. Replies to email threads go through email's `sendTransactional` with template `crm.inbox_reply`; Meta replies through the Meta Send API within its 24-hour window, else the reply button is disabled with the reason.
51. (R4) An AI draft is never sent by the system: staff edit and press Send, which records `ai_draft_status = used`. No draft is requested when the thread `is_sensitive` or the deterministic keyword screen (`SENSITIVE_KEYWORDS` per locale) matches, unless `settings.ai.sensitive_enabled` is true; the status becomes `blocked_sensitive`.

**Identity additions (V1)**
52. Changing a person's email (staff `updatePerson`) calls platform's `syncCustomerAccountEmail(ctx, { personId, email })` in the same transaction; when the new address belongs to another user the action fails with `conflict` before any write. The old address keeps its suppressions (they are keyed by hash); the new address is checked against `suppressions` on the next send.
53. A marketing grant (`newsletter|events|member_comms|b2b`) for a person whose `birth_on` makes them younger than 13 on `recorded_at` (Belgian age of digital consent, law of 30 July 2018, art. 7) is not recorded: `recordConsent` returns `skipped_minor` and the form or portal shows "A parent or guardian must give this consent". Persons without `birth_on` are treated as adults. A guardian records the grant for the minor from reception with a `guardian_consent` declaration present.
54. Declarations: `person_declarations` holds only `guardian_consent` (cross-module D15). `recordDeclaration` appends a row for the current published version from `site.getCurrentLegalVersion(db, 'guardian_consent')` (`{ versionId, version, requiresReacceptance, text }`). `hasValidDeclaration(db, { personId, kind: 'guardian_consent' })` is true when `v_declaration_current.is_valid` and its `document_version_id` is the current version or one the site marked as not requiring re-acceptance. A new version that requires re-acceptance makes every earlier acceptance invalid at once. Revoking appends `status = revoked`. House rules and the health self-declaration are site's `terms` (`site.hasAcceptedCurrentTerms(db, personId)`) and the detailed health declaration is forms' `health-declaration` form (`forms.hasValidSubmission(db, { personId, formSlug: 'health-declaration' })`); crm records neither and only reports them in `getReceptionCard`.
55. `emergency_contact` is shown to staff with `persons.read` on the 360 header and the reception quick view; it is never in segments, exports for staff, AI context or emails, and erasure nulls it.

**Release 3 and 4 additions**
56. (R3) B2C playbook: `crm.apply_b2c_playbook` (every 5 minutes) reads `activity_events` of kind `ops.stage_changed` from the last 30 minutes and, for each one whose `data.to` has an active `b2c` playbook stage, creates one task for the stage's `owner_role` titled from `required_action`, due `deadline_days` later (dedupe `playbook:b2c:<person_id>:<to_stage>:<event_id>`), and enrols the person through automation's `enrolPersonBySlug` when the stage has an `automation_slug`. The 30-minute window overlaps the 5-minute cadence, and the dedupe key makes the overlap harmless. A stage whose task stays open longer than `escalation.after_days` is escalated like rule 3.48.
57. (R3) Inbox states: `open → pending` (staff reply), `pending → open` and `resolved → open` (new inbound message), `open|pending → resolved` (staff, or `crm.close_stale_threads` after 14 days `pending` without inbound), `resolved → open` (staff reopen). An `open` thread with no staff reply 24 hours after its oldest unanswered inbound message (`settings.business_hours` respected: hours outside opening time do not count) is escalated once by `crm.escalate_threads`: `escalated_at` set, one task kind `follow_up` priority `high` for the assignee (else the first active `customer_service` user), one `notify.slack` line (fingerprint `inbox:<thread_id>:escalated`), and the event `inbox.escalated` on the linked person (dedupe `inbox:<thread_id>:escalated`). A staff reply clears nothing; `escalated_at` stays for reporting.
58. (R4) The AI draft context is: `toAiContext(person)` (which already carries packages, credits, bookings and membership fields), the last 10 non-note messages of the thread, and the active `support_knowledge_articles` in the thread's locale, cut to 20,000 characters in `sort` by key. Articles are BEAM policy; they never contain person data.

## 4. Server surface

Files: `apps/web/modules/crm/{actions,queries,api,jobs,schedules,events,permissions,nav,privacy,seed}.ts` are barrels or registries; the code lives in area folders `apps/web/modules/crm/<area>/{actions,queries,api,jobs}.ts` with areas `persons`, `tags`, `consent`, `duplicates`, `sensitive`, `timeline`, `segments`, `tasks`, `companies`, `pipeline` (R3), `inbox` (R3). "Audit" names the `audit_log.action` value (staff writes only, by the wrapper or `ctx.audit`).

### 4.4 Route handlers

| Route | Method | Behaviour |
| --- | --- | --- |
| `app/api/public/unsubscribe/[token]/route.ts` | POST | RFC 8058 one-click (`List-Unsubscribe=One-Click` body). Resolves the token, withdraws the message's purpose (rule 3.16) with method `unsubscribe_link`, source `one_click:<email_message_id>`, and returns 200 with an empty body. An unknown token also returns 200 and writes nothing (no enumeration, mail clients do not retry). Never needs a session. |
| same | GET | Never mutates (link scanners). 303 to `/{locale}/preferences/{token}?confirm=unsubscribe`. |
| `app/api/public/preferences/[token]/route.ts` | GET | `{ firstNameInitial, locale, purposes: Record<MarketingPurpose, boolean>, suppressedAll, confirmPurpose }`; unknown token → 404 |
| same | POST | `{ purposes: Record<MarketingPurpose, boolean>, locale?, unsubscribeAll?: boolean }` → 200 `{ ok: true }` through `updatePreferencesByToken`. A token whose message was sent more than 365 days ago → 410 for everything except unsubscribing, and the page offers "email me a fresh link" (`crm.preference_link` template, rate limited to 3 per person per day with platform's `rateLimit`). |
| `app/api/webhooks/meta/route.ts` (R3) | GET / POST | GET answers `hub.challenge` when `hub.verify_token = META_VERIFY_TOKEN`. POST is a one-liner over platform's `handleWebhook(req, { provider: 'meta', verify })`: `verify` checks `X-Hub-Signature-256` with `META_APP_SECRET` and returns `externalEventId = entry.messaging[].message.mid`; platform inserts `webhook_events` on conflict do nothing, enqueues `webhook.process` with key `webhook:meta:<mid>` and answers 200 within 2 s. |

Preference and unsubscribe tokens follow the architecture's stored-hash pattern and are the email module's per-message link tokens: every email (marketing or transactional) gets a random 32-byte token whose sha256 is `email_messages.link_token_hash`. crm resolves it with email's `resolveLinkToken(db, token): Promise<{ emailMessageId: string; personId: string; purpose: MarketingPurpose | null; locale: Locale; sentAt: Date } | null>` (a transactional message has `purpose = null`, so its link opens the centre without a pre-selected purpose). Tokens are multi-use and idempotent: a second unsubscribe is a no-op, never an error. Tokens of a merged person resolve to the winner through `resolveCanonicalPersonId`. When the message row has been purged by email's retention, the token is unknown and the page offers "email me a fresh link" after the visitor types their address (the reply is the same whether or not the address exists).

### 4.6 Segment compiler

`packages/core/src/crm/segments/` (pure): `SegmentRuleSchema` (Zod), `SEGMENT_ALLOWED_FIELDS`, `SEGMENT_ALLOWED_EVENT_KINDS`, `compileSegment(rule, { now }): SqlFragment` where `SqlFragment = Array<string | { param: unknown }>`; `apps/web/modules/crm/segments/sql.ts` turns it into a Drizzle `SQL` with `sql.join`, so every value is a bound parameter and core never imports Drizzle.

```ts
type SegmentRule =
  | { op: 'and' | 'or'; rules: SegmentRule[] }
  | { type: 'not'; rule: SegmentRule }
  | { type: 'field'; field: AllowedField; cmp: Comparator; value?: unknown }
  | { type: 'tag'; tagKey: string; has: boolean }
  | { type: 'consent'; purpose: ConsentPurpose; granted: boolean }
  | { type: 'in_segment'; segmentId: string; negate?: boolean }
  | { type: 'event'; kind: AllowedEventKind; mode?: 'live' | 'replay' | 'on_demand';
      where?: Partial<Record<AllowedEventDataKey, string | number | boolean | { gte?: number; lte?: number }>>;
      withinDays?: number; minCount?: number; negate?: boolean };
```

Comparators by field type: `enum`/`text`: `eq|neq|in|not_in|is_null|is_not_null`; `number`: `eq|neq|gt|gte|lt|lte|between|is_null`; `timestamp`: `before|after|within_last_days|more_than_days_ago|within_next_days|is_null|is_not_null`; `text[]`: `contains_any|contains_all|contains_none`; `boolean`: `is_true|is_false`.

`SEGMENT_ALLOWED_FIELDS` is built from ops' `PERSON_PROFILE_COLUMNS` (`packages/core/src/ops/profile-fields.ts`), filtered to these columns of `v_person_profile`, with the names ops uses: `status`, `is_member`, `membership_status`, `membership_period_end_at`, `b2c_stage`, `locale`, `country`, `postal_code`, `city`, `acquisition_source`, `acquisition_campaign`, `acquisition_medium`, `created_at`, `revenue_cents`, `lifetime_value_cents`, `purchases`, `visits`, `events_attended`, `no_shows`, `avg_order_cents`, `first_purchase_at`, `last_purchase_at`, `first_visit_at`, `last_visit_at`, `last_activity_at`, `days_since_activity`, `next_booking_at`, `has_future_booking`, `credits_day_remaining`, `credits_night_remaining`, `credits_euro_remaining`, `next_grant_expires_at`, `package_product_ids`, `tags`, `consent_newsletter`, `consent_events`, `consent_member_comms`, `consent_b2b`, `is_suppressed_all`, `is_company_contact`, `has_waitlist_waiting`, `last_assessment_form_slug`, `last_assessment_outcome_key`, `is_tester`; R2 `webinars_registered`, `webinars_attended_live`, `webinars_watched_replay`. `package_product_ids uuid[]` (product ids of the person's usable grants, blueprint 6 "package type") is the one column crm asks ops to add. Each entry carries `{ column, type, label: i18nKey, options? }`; `segment-fields.test.ts` fails when a listed column is missing from `PERSON_PROFILE_COLUMNS`. Blueprint 6 statuses map as follows: lead, customer and member are `status`; prospect, new customer, first-time visitor, active, repeat, dormant (`retention`), reactivation candidate and lost are `b2c_stage` values (ops); package holder is `credits_day_remaining > 0 or credits_night_remaining > 0`; VIP is the system tag `vip`; referral activity is the event rule over `referral.attributed` (R3); B2B relationship is `is_company_contact`.

`SEGMENT_ALLOWED_EVENT_KINDS` uses the kinds exactly as their owners declare them: booking `booking.confirmed|attended|check_in_undone|no_show|cancelled|late_cancelled|event_ended` and `waitlist.joined|offered|confirmed|expired|requeued|released|withdrawn` (booking section 4.7; `waitlist.expired`, not `offer_expired`); commerce `order.paid`, `checkout.abandoned`, `promotion.redeemed`; credits `credits.threshold_reached`, `credits.grant_expired`, `credits.share_added` (credits' names; not `credits.expired` or `credits.shared`), `membership.started`, `membership.renewed`, `membership.cancelled`, R3 `referral.attributed`; forms `form.started`, `form.completed`, `form.abandoned`, `form.result_viewed`, `assessment.result_generated`, `assessment.cta_clicked` (forms section 3 E table); email `email.opened`, `email.clicked`; ops `ops.stage_changed`; webinar (R2) `webinar.registered|started|attended|watched|no_show|poll_answered|cta_clicked|question_asked|chat_posted` (webinar's authoritative list, its decision 9; there is no `webinar.cta_shown` event, CTA impressions stay in `webinar_interactions`; `webinar.attended` is written per mode, so `mode` filters live, replay and on-demand attendance). Allowed `where` keys are declared per kind in `SEGMENT_EVENT_DATA_KEYS: Record<AllowedEventKind, string[]>` with the key spelling of the writer's `data` schema (for example `form_slug`, `outcome_key`, `funnel`, `form_kind` and `cta_key` for `form.*` and `assessment.*`, `poll_key`, `option_keys`, `option_key`, `cta_key`, `threshold` and `watched_sec` for webinar, `session_kind`, `session_id`, `event_category`, `owner_person_id`, `is_guest`, `is_first_booking`, `is_first_visit` and `queue` for booking and waitlist, booking rule R61); `segment-events.test.ts` asserts every kind exists in `registry/events.generated.ts` and every key exists in that kind's declared `data` schema. A key holding an array (`option_keys`) compiles to `e.data->$key ? $val`; the scalar `option_key` (the single chosen option, null for a multi-option answer) compiles like any other key. A numeric key (`watched_sec`) accepts `gte`/`lte` and compiles to `(e.data->>$key)::numeric >= $val`. An event rule compiles to `(select count(*) from activity_events e where e.person_id in (select id from persons where id = v.person_id or merged_into_person_id = v.person_id) and e.kind = $k and not e.is_sensitive [and e.mode = $m] [and e.data->>$key = $val] [and e.occurred_at >= $now - $days]) >= $min`. This is how webinar attendance, watch thresholds, poll answers, CTA activity, assessment outcomes, event participation and waitlist state become segmentable (blueprint 6).

The outer query is `select v.person_id from v_person_profile v join persons p on p.id = v.person_id where p.erased_at is null and p.merged_into_person_id is null and p.processing_restricted_at is null and (<compiled>)`.

Timeline categories, by the kind's prefix before the dot: `profile` (person, tag, segment, sensitive, declaration, ops), `bookings` (booking, waitlist), `purchases` (checkout, order, payment, refund, promotion, pos, invoice, credit_note, credits, membership, referral), `email`, `webinar`, `forms` (form, assessment), `automation` (items from `getTimelineItems`), `service` (note, interaction, task, inbox), `consent` (consent, suppression, privacy), `b2b` (company, opportunity). A prefix not in this map falls into `profile`; `timeline.test.ts` asserts every registered prefix is mapped.

## 11. Edge cases and failure modes

1. **Two forms submitted at the same second with one new email.** The advisory lock serialises them; one creates, the other finds. Both submissions link to the same person.
2. **Same email typed with capitals or spaces.** Stored trimmed and lower-cased; uniqueness is on `lower(email)`; no duplicate.
3. **Staff edits a person while a customer edits their profile.** Both send `version`; the second write gets `conflict` and the form reloads with the newer values.
4. **Staff changes an email to one used by another active person.** `conflict` "This email belongs to C-000456" with a link to merge.
5. **A waiting lead buys a package.** Without an override, the derived status becomes `customer` at payment and booking's queue logic reads the new status; confirmed seats are untouched because crm never edits bookings (R2 acceptance "waiting lead who buys is reclassified correctly"). With an override `lead`, the override stays, the person appears in `v_status_override_conflicts` and the 360 banner, and staff decide.
6. **Unsubscribe link clicked by a corporate link scanner.** GET only redirects; only a POST or the confirm button unsubscribes.
7. **One-click unsubscribe for a person who was merged.** The token's person id resolves to the winner; the winner is unsubscribed.
8. **Unsubscribe for an address that is already suppressed.** Suppression insert does nothing; the withdrawal row is still appended if consent was granted; `addSuppression` still calls `automation.requestSuppressionExit` with the existing suppression id (the key `supp:<suppression_id>` dedupes).
9. **Re-import from Mailchimp marks an unsubscribed person "subscribed".** The import consent grant is skipped with `skipped_suppressed`; the import report lists it; acceptance test "suppression survives an import".
10. **Person unsubscribes, later ticks "newsletter" on a website form.** The grant returns `needs_confirmation`, `crm.confirm_resubscribe` is sent (a transactional email, allowed despite the scoped suppression); only the click records the grant.
11. **Hard bounce on an address, the person then changes email.** The new address has a new hash and is reachable once consent exists; the old suppression stays.
12. **Merge where both persons have an active membership.** Refused with "Both persons have an active membership. Cancel one first."; nothing changes.
13. **Merge of A into B, then B into C.** The second merge also points A at C; `resolvePersonIds(C)` returns C, B and A; the timeline shows all three histories.
14. **Merge loser had newer withdrawn newsletter consent than winner's grant.** The withdrawal is copied to the winner; the merged person is not reachable for newsletter.
15. **A module adds a new table with `person_id` after crm shipped.** Merge discovers it from `information_schema` and repoints it by default; `merge-coverage.test.ts` fails if the table has a unique key including the person column and no merge strategy in `MERGE_STRATEGIES`, so the owner adds one.
16. **Sensitive note created by a user who lacks `persons.sensitive_read`.** The sensitive toggle is hidden; the server refuses with `forbidden` if sent anyway.
17. **`SENSITIVE_DATA_KEY_V1` missing in an environment.** `addNote` with `isSensitive` and `setSensitiveField` fail with `internal` (platform's `encryptSensitive` throws `PermanentError('missing_key')`) and a Sentry event; non-sensitive work continues; platform's health check returns 503 in production (platform edge case 18).
18. **Segment rule references a field ops has not shipped yet.** The registry test `segment-fields.test.ts` fails at the wave gate; at runtime the compiler rejects unknown columns with `validation`.
19. **Segment refresh of 50,000 persons times out.** Statement timeout 45 s inside the 60 s job; `refresh_error` recorded, members kept, retried next hour; the segment page shows the error and the last good count.
20. **A segment used by a scheduled campaign is archived.** `archiveSegment` refuses with the campaign name.
21. **Segment A excludes B and B excludes A.** Allowed (exclusions are one level and not recursive); `in_segment` cycles are refused on save.
22. **Task owner is disabled.** Tasks stay; `/admin/tasks` "All" shows them with owner "(disabled)"; reassignment needs `tasks.all`.
23. **Automation creates the same follow-up task twice after a job retry.** `dedupe_key` unique; second insert returns `created: false`.
24. **Company contact leaves the company.** `endContact` sets `ended_on`; history and timeline stay; the person keeps every B2C relationship.
25. **Two companies with the same VAT number typed differently (`BE 0123.456.789`, `be0123456789`).** Normalised to `BE0123456789`; the second save gets `conflict`.
26. **Preference link from an email sent more than 365 days ago.** Unsubscribe still works; other changes need a fresh link sent to the person's address. When email's retention has purged that message, the token is unknown: the page asks for the address and sends a fresh link if it exists, with the same reply either way.
27. (R3) **Inbound email from an unknown sender.** Thread created with `person_id` null; staff link or create; no consent is recorded.
28. (R3) **Meta webhook delivered twice.** `webhook_events` unique `(meta, mid)` and `external_message_id` unique; one message.
29. (R4) **Customer email mentions burn-out.** Keyword screen matches; `ai_draft_status = blocked_sensitive`; staff write the reply manually; nothing is sent to Claude.
30. **Erasure of a person who is a company's primary contact on an open opportunity.** The opportunity stays with `primary_contact_person_id` null; the pipeline card shows "No contact".
31. **A 12-year-old ticks "newsletter" on the website form.** `birth_on` is known: `recordConsent` returns `skipped_minor`, nothing is recorded, the form shows the guardian message. Without `birth_on` the grant is recorded (decision 42).
32. **Site publishes a new guardian-consent version that requires re-acceptance.** Every earlier guardian consent stops counting at once; `getReceptionCard` reports `guardianConsentValid: false`, the check-in desk shows a warning and reception records a new consent with method `reception`. A new house-rules version is site's `terms` and shows as `termsAccepted: false` (from `site.hasAcceptedCurrentTerms`). Booking decides whether to block; crm only reports the three states in `getReceptionCard` (cross-module D15).
33. **Staff change the email of a person who has a portal login.** `syncCustomerAccountEmail` moves the login to the new address in the same transaction; if another user already has that address, nothing changes and the action returns `conflict`.
34. **A scheduled and a manual refresh of one segment start in the same second.** The advisory lock makes the second wait; it then computes the same set and writes no events (dedupe keys).
35. **Unsubscribe in a transactional email (no purpose).** The link opens the preference centre without a pre-selected purpose; the one-click POST is not offered for transactional messages (email sends no `List-Unsubscribe` header on them).
36. (R3) **`apply_b2c_playbook` runs twice over the same 30-minute window.** The task dedupe key `playbook:b2c:<person_id>:<stage>:<event_id>` makes the second run create nothing.
37. (R3) **A thread is escalated, then the customer writes again.** The thread stays `open` with `escalated_at` set; no second escalation happens for that thread.

Choices the inputs left open:

9. Status: crm never stores the derived status; `v_person_status` stays in credits as the architecture says. crm narrows the architecture's "any paid order" to the blueprint's "paid for a session, package, night or membership" (rule 3.8): orders of only merchandise or vouchers do not make a customer, legacy purchased or imported day and night grants do. Member pricing and member-only access use the real membership (`is_member`), not the override; classification, lead windows and content blocks use `coalesce(override, derived)`.
10. An override that diverges from the derived status is surfaced (banner, `v_status_override_conflicts`), never auto-cleared. Automations may set an override only when none exists.
11. Acquisition is immutable after creation; staff may only fill a missing source. On merge the older person's acquisition wins.
12. Locale on an existing person is never overwritten by later forms or imports.
13. Customers cannot change their email in the portal in V1; staff do it (avoids an unverified-address takeover path).
14. Suppression lifting: suppressions are never deleted; only a scoped `unsubscribe` suppression yields to a newer explicit grant through portal, preference centre, or a form confirmed by email (double opt-in). `all`, bounce, complaint, manual and erased suppressions are permanent for the address.
15. Imports never lift a suppression and never override a withdrawal; they also never write suppressions except the `suppressions` import kind.
16. Staff may record a grant only for `b2b`, on legitimate interest. Other purposes need the person's own action.
17. Preference and unsubscribe links use the architecture's stored-hash pattern through email's per-message link token (`email_messages.link_token_hash`, resolved by `email.resolveLinkToken`): no extra table, because the message row exists anyway, and the source of every one-click withdrawal names the message (`one_click:<email_message_id>`). Tokens are multi-use and idempotent, not single-use, because an unsubscribe link must keep working. Unsubscribe works as long as the message row exists; changing other preferences needs a message younger than 365 days; otherwise the person asks for a fresh link.
18. One-click unsubscribe mutates only on POST; GET redirects to a confirm page, so mail scanners cannot unsubscribe people.
19. Duplicate scoring uses fixed rules and weights (95/90/80/70/50, threshold 50), no fuzzy matching and no `pg_trgm`. Search uses the built-in `tsvector` with the `simple` configuration, so PGlite and Neon behave the same.
20. Merge is generic: crm discovers every foreign key to `persons.id` from `information_schema` and repoints mutable tables, with `MERGE_STRATEGIES` for tables with person-including unique keys and a coverage test. Append-only tables are not rewritten; reads resolve merges through `resolvePersonIds` (one level, because merges flatten chains). This keeps the `beam.allow_rewrite` bypass exclusive to erasure, for crm and for the owner merge hooks it calls (decision 52).
21. Merge refuses when both persons hold an active membership, an active booking for the same session, or a place on the same waitlist; staff resolve those first.
22. A customer `users` row of a merged loser is repointed to the winner, so both logins see one record.
23. Sensitive fields are read and written with the same permission, `persons.sensitive_read`.
24. Segments are edited with `email.write` (marketing and customer service have it); no new permission string.
25. Segment members store the raw set; exclusions apply at read time through `segmentAudienceSql`, so a change to an excluded segment takes effect without refreshing the including segment. Exclusions are one level; `in_segment` references are checked for cycles.
26. Event-based segment rules over `activity_events` give webinar, poll, CTA, assessment, event and waitlist segmentation without widening `v_person_profile`.
27. The segment refresh runs at minute 7 of every hour, not minute 0, to stay clear of other hourly work; statement timeout 45 s.
28. Tasks: without `tasks.all` users see and create only their own tasks. Overdue is computed, not stored. No task emails; the navigation badge and the ops action dashboard surface them.
29. Companies ship in V1 (partners, holds and B2B invoices need them); opportunities, board and playbook ship in R3. Playbook editing needs `settings.write`.
30. The playbook defines stages for both pipelines; B2C stage keys are ops' `b2c_stage` values. A stage change creates exactly one task for the opportunity owner and optionally enrols the primary contact.
31. Inbound email arrives through Resend Inbound on `inbox@in.beam.be` via the email module's existing webhook; crm exposes `ingestInboundEmail`. Attachments are counted, not stored. Inbound messages never create persons or consent.
32. Website contact forms reach the inbox when the form version sets `FormSettings.createInboxThread: true` in forms' versioned `FormDefinition` (cross-module D62; `definition.settings.inbox` does not exist).
33. AI drafts (R4) are generated only on request (`ai.use`), never automatically, to control cost; a keyword screen and the thread's `is_sensitive` flag block drafting unless sensitive processing is enabled in settings.
34. Erasure deletes consent records (the hash-only `erased` suppression keeps the objection), deletes the timeline and tasks, anonymises `persons`, keeps `acquisition.source/campaign/medium` for aggregate attribution, and nulls the opportunity contact.
35. Retention: inactive profiles are anonymised by ops' `ops.marketing_profile` (3 years) and leads by ops' `ops.marketing_contact` (2 years), both with candidates from crm's `listInactiveProfiles`; crm's former key `crm.inactive_profile` is dropped so whole-profile erasure has one owner. crm's own keys are declared in `privacy.ts` (`retention`): closed duplicate candidates deleted after 1 year (`crm.duplicate_candidates_closed`), closed tasks after 2 years (`crm.tasks_closed`), resolved inbox threads after 2 years (`crm.inbox_resolved`), superseded declarations after 3 years (`crm.declarations_superseded`); suppressions (`crm.suppressions`) and consent records (`crm.consent_records`) are `keep`.
36. The 360 page reads sibling modules only through their `api.ts`, wrapped in `safePanel()`, so crm ships independently of their build order.
37. Tests that need ops' `v_person_profile` or credits' `v_person_status` before those modules land create fixture views with the contract columns in the test database.
38. Phone normalisation is a small in-house Belgian-first normaliser in `@beam/core/crm` (no new dependency).
39. The crm catalogue is written in full by crm-P1 and reconciled by crm-P7, so parallel packages never edit the same JSON file.
40. crm never stores the national register number, eID data or ID-card copies; nothing in BEAM's processes needs them and they raise the breach impact.
41. platform's `readSensitive` stays the one reader of sensitive data, with platform's signature for every module (cross-module D11): `readSensitive(ctx: Ctx, personId: string, purpose: 'staff_view' | 'privacy_export' | 'subject_result', scope?: { keys?: SensitiveFieldKey[]; eventIds?: string[]; submissionIds?: string[] }): Promise<SensitiveBundle>` returning `SensitiveBundle = { fields: Partial<Record<SensitiveFieldKey, string>>; formAnswers: { submissionId; fieldKey; value }[]; notes: { eventId; body }[] }`. `staff_view` needs a staff actor with `persons.sensitive_read`; `privacy_export` needs the system actor; `subject_result` (forms' result page) needs the system actor and a non-empty `submissionIds` of the person's own submissions. The purposes `care` and `customer_request` and a bundle field `events` do not exist. crm's staff reveal uses `staff_view` and maps `notes` straight from the bundle. `encryptSensitive`/`decryptSensitive` come from `apps/web/lib/sensitive.ts` through platform's `api.ts`, not from `@beam/core/privacy`.
42. Marketing consent needs the person to be 13 or older when `birth_on` is known (Belgian Data Protection Act of 30 July 2018, art. 7). Without a birth date the person is treated as an adult; BEAM asks the birth date only where it is useful (nights, memberships).
43. Guardian consent for minors is a versioned acceptance (`person_declarations`, kind `guardian_consent` only) of site's legal page, not a consent purpose: it rests on contract and safety, not on consent. House rules and the health self-declaration are chapters of site's `terms` (`site.hasAcceptedCurrentTerms`) and the detailed health declaration is forms' `health-declaration` form (`forms.hasValidSubmission`, 365-day validity); crm stores neither and has no `acceptMyDeclaration`. Whether a missing declaration blocks a booking or a check-in is booking's decision; crm shows the state in `getReceptionCard` (cross-module D15).
44. Restriction of processing has one flag, `persons.processing_restricted_at`, written by `restrictProcessing`; ops' `processing_restrictions` row holds the request details and is written in the same transaction. That flag is the single source every reader uses: `v_suppression_status` (and through it email's `v_marketing_reachability`), the segment compiler's outer query, ops' `v_person_profile`, staff exports and automation's enrolment check (A-11) and `processing_restricted` condition. No module reads `processing_restrictions` to decide reachability; the two can never disagree because ops writes both in one transaction.
45. B2C playbook tasks come from a 5-minute job over `ops.stage_changed` events with a 30-minute look-back and per-event dedupe keys, so crm needs no cursor setting and a missed tick loses nothing.
46. Inbox escalation: one escalation per thread when no staff reply arrives within 24 opening hours (`settings.business_hours`), as a high-priority task plus one Slack line.
47. The AI draft knowledge base is a small crm table edited by staff (`support_knowledge_articles`), included whole in the prompt up to 20,000 characters; no vector search and no embeddings.
48. The timeline merges automation's `getTimelineItems` (automation writes no `activity_events`) and lists other modules' event kinds by reference to their own specs, so crm keeps no copy that can drift; segment event rules use the writers' exact kind names and `data` keys, checked by a registry test.
49. Partner management in crm is limited to partner companies and the persons they referred; referral codes, rewards, commission and partner performance are credits' (R3).
50. Customer-facing crm pages meet WCAG 2.1 AA and are checked with axe in the crm end-to-end spec.
